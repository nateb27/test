# Design: rules as implemented

This file records the game rules as they actually work in code. `docs/PLAN.md` is the intent; when implementation differs or a rule is clarified, update this file in the same change.

## Status

Phase 0 (scaffold and contracts) only. No game rules are implemented yet; the sim creates the initial state and advances the tick.

## Contract decisions made in Phase 0

- **Build command places the foundation immediately.** When a `build` command is applied, the sim validates with `canPlace`, deducts the cost, creates the foundation and gives each unit a `build` order referencing it. `assist` on an unfinished building behaves the same as `build`; `assist` on a completed farm becomes a `gather` order on it.
- **Farms are buildings** with a `farm` ability; `gather` orders target either a resource node or a completed farm building.
- **Path requests are atomic.** A request is started only while budget remains and always completes within the tick, so no partial A* state is saved. The queue (`state.pathQueue`) and `occupancyVersion` are in state so save/load continues identically.
- **Cheats are commands** (`type: 'cheat'`) and cheat flags live in `PlayerState.cheats`, so replays and saves stay exact. The client only exposes them in dev/e2e builds.
- **Production timing**: each queue item stores integer `ticksDone`/`ticksTotal`; `ticksTotal = max(1, round(seconds * TICK_RATE))` fixed at enqueue. Construction progress is a float in [0, 1] (multi-builder speed is fractional), clamped to exactly 1 on completion.
- **Modifier selection**: a modifier matches a def if the def's id is in `select.ids` OR the def has any tag in `select.tags`. Resolution: base, then civ, then tech modifiers; all `add` before all `mul`. Resolved costs are rounded with `Math.round`.
- **Player ids** equal their index in `players`; 0 is the neutral owner of resource nodes (`civ: null`), real players are 1..n.
- **Save format**: canonical JSON of `{ version, state }`; unknown versions are refused.

### WP4: content data

- All plan section 5 content is in `src/data/`. Tech rates use `mul` modifiers selected by the `villager` tag (Iron Axes etc. stack multiplicatively; Hand Carts adds 5 carry capacity and multiplies speed by 1.1). Themata is `cost.wood x0.8` on `farm` (50 -> 40) plus `gatherRate.farm x1.1`.
- Age-advance techs (`townshipAge`, `citadelAge`, `empireAge`) are researched at the Town Center. Their `age` is the age the player must currently be in (they set `advancesTo = age + 1`), and `requiresAgeBuildings: 2`. Buildings with `countsTowardAge` are Mill, Lumber Camp, Mining Camp, Farm, Barracks (age 1), Archery Range, Stable (age 2), Siege Workshop and Silk Workshop (age 3); the Town Center and House do not count.
- The Silk Workshop is defined in `civs/byzantines.ts` and included in the shared `buildings` table (with `civs: ['byzantines']`); every villager lists it in `builds`, availability filters by civ. The Stable trains Horseman, Lancer and Cataphract; the Cataphract `replaces` the Lancer. The Siege Workshop trains Battering Ram, Trebuchet and Siphonarios.
- Node ids: `tree`, `berryBush`, `goldDeposit`, `stoneDeposit`. Icons for nodes: `icon.node.<id>`.
## WP1 (sim core) rules

- **Command intake.** Commands sort by `(playerId, seq)` (stable). A command is dropped with `CommandRejected('invalidCommand')` before dispatch if its type is unknown, `playerId` is not a real player (1..n), `seq` is not an integer, a number is not finite, an id is not a positive integer, an id list is empty, or a required string/flag is missing. Rule checks (ownership, cost, placement) belong to the handlers.
- **Map generation.** Defs are found through the registry: the Town Center is `start.centerBuilding`; node defs are chosen by `gatherKind` (`wood`, `berries`, `gold`, `stone`), not by id. A kind with no def is skipped. Attempt k uses `rng = createRng(seed + k)`; `state.mapSeed` is the final seed (up to 24 attempts, then the last map is kept).
- **Start positions.** One player: a corner start chosen by the seed; two players: opposite corners. Each start gets 0..8 tiles of inward jitter. Edge distance is `min(25, floor(size / 4))` (25 on the 120 map), measured to the Town Center centre.
- **Clear radius.** Nothing is generated within 8 tiles of a Town Center centre except the two guaranteed berry patches, which the plan places at 6 to 10 tiles. Gold (10 to 14), stone (12 to 16) and the three tree stands (8 to 14) are outside it. Distances are node centre to Town Center centre.
- **Clusters.** Berries: 3x2 or 2x3 block; gold: 2x2 block of deposits; stone: L of three deposits; tree stands and forests: seeded blobs. Different clusters are separated by at least one free tile, and every blob tile keeps an open edge neighbour. Forests keep 15 tiles from starts and cover about 12% of tiles. Extra gold, stone and berry clusters (4, 3, 4 on 120x120, scaled by area) keep 20 tiles from starts and 14 from each other.
- **Validation.** 4-connected flood fill from the first Town Center must reach at least 95% of free walkable tiles; every Town Center, starting unit and guaranteed node must have a reachable edge-adjacent tile.
- **Starting units** stand on the ring of tiles around the Town Center, evenly spaced from a seeded offset, facing 1.
- **Delete.** All-or-nothing per command: unknown id gives `unknownEntity`, a foreign or neutral id gives `notOwner`. Unfinished buildings refund `costPaid` immediately; removal itself happens in cleanup.
- **Cleanup.** Removes depleted nodes (`amount <= 0`) and `pendingRemoval`, emits `ResourceNodeDepleted`, calls `endCurrentOrder` for removed units, clears their gatherer/builder slots and path requests, frees blocking footprints and bumps `occupancyVersion`. Orders of surviving units that point at a removed entity are not touched: order handlers treat a missing target as retarget-or-finish.
- **Queries.** `entitiesInRect` and `entityAtPoint` use half-open footprints `[tx, tx+size)`; units use `UNIT_PICK_RADIUS` (rect test: distance from the unit to the rect).
- **spawnUnit cheat** creates the unit at the exact point; rejects unknown unit types (`unknownDef`) and out-of-map or blocked tiles (`invalidTarget`).
### WP2: pathfinding and movement

- **A\***: 8-connected, integer costs 10 straight / 14 diagonal, octile heuristic to the goal rectangle. A diagonal step needs both orthogonal tiles walkable (no corner cutting). Open-list ties: lowest f, then lowest h, then lowest tile index. Walkable = in bounds and `runtime.occupancy` is 0 (terrain walkability is not consulted; M1 is all grass).
- **Goals**: a `point` goal is the tile containing the (clamped) point; a `footprint` goal is any tile in the 8-connected ring around the footprint, corners included.
- **Unreachable goal**: the path leads to the expanded tile with the lowest octile distance to the goal, ties by lowest path cost, then lowest tile index.
- **Blocked start** (unit standing on a fresh foundation): the search starts from the nearest walkable tile (squared distance, ties by tile index) and the unit walks there first.
- **Smoothing**: greedy string pulling over the A* tiles; a segment is kept only if an integer supercover walk between tile centres touches only walkable tiles, and a segment passing exactly through a tile corner also needs both side tiles walkable. Waypoints are tile centres without the start tile; a reached `point` goal ends at the exact point.
- **Request queue**: FIFO, budget `PATH_BUDGET_PER_TICK` expanded nodes per tick. Each search is capped at the remaining budget; if it would exceed it, its result is discarded and the request stays at the head of the queue for the next tick (a discarded search's expansions still count, so a tick never exceeds the budget). The first search of a tick runs with the full budget and is always used (if it is still capped, its best partial path is used; impossible on 120x120). The search starts from the unit's current tile (it stood still while waiting).
- **Following**: walking orders call `followPath(ctx, unit, goal)` every tick (`path/follow.ts`). When `occupancyVersion` changed since the path was computed, all remaining segments are re-checked; if any is blocked a new path is requested, otherwise the path's version is refreshed. Movement also stops a unit whose next segment became blocked.
- **Approach tile**: walkable ring tile in the same connected component as the origin's tile (any walkable ring tile if the origin's tile is blocked, e.g. a building centre), nearest by squared distance from the origin to the tile centre, ties by tile index; `null` if none.
- **Group move slots**: walkable tiles ordered by squared tile distance from the clicked tile, ties by tile index, restricted to the clicked tile's component when that tile is walkable. Slot 0 is the exact clicked point when its tile is walkable, others are tile centres. Units sorted by squared distance to the clicked point (ties by id) take slots in order, so the nearest unit gets the clicked point. Slots repeat only if the component is smaller than the group.
- **Commands**: `move` and `stop` are all-or-nothing: any unknown id rejects with `unknownEntity`, a foreign id with `notOwner`, a non-unit with `cannotPerform` (first failing id in ascending order); `move` with non-finite coordinates rejects with `invalidCommand`. Duplicate ids are ignored.
- **Movement**: speed = resolved `speed` stat from the runtime cache, else the unit def, else 1 tile/s; a unit may pass several waypoints in one tick. Facing comes from the tick's displacement: a component counts when it exceeds 0.4x the other (octant boundary ~22 degrees).
- **Separation**: only idle units (no order, empty queue, no path, no pending request). Pairs closer than `SEPARATION_RADIUS` each move half the overlap apart (coincident units split along one of 8 directions picked by `higherId % 8`); pushes are summed then applied, and a push ending on a blocked tile is skipped. Pairs are found with a per-tick tile hash (scratch, not state).
## WP3: renderer and placeholder art

- **Layers** (all in world-pixel space, moving with the camera, back to front): `terrain` (16x16-tile baked chunks, at most 30 live, off-screen ones hidden), `groundOverlays` (empty, for WP10 rings/placement/rally), `entities` (depth sorted), `worldOverlays` (empty, for WP10 bars/markers). Exposed as `renderer.layers`.
- **Depth**: sprites sort by `x + y` of the anchor (unit interpolated position, footprint centre for buildings and nodes), ties by id. Footprints and sprite ids come from `registry.def(typeId)` and fall back to `DEFAULT_FOOTPRINT` / `'<kind>.<typeId>'` when a def is missing.
- **Animation state** is derived from the unit: moving (pos differs from prevPos, or a path is being followed) is `walk`, or `carry` when carrying; gather `harvesting` and build/assist `building` phases are `work`; otherwise `idle`. Buildings under construction show `foundation` below 30% progress, `scaffold` after.
- **Team colour**: sprites are generated per team colour on demand (`teamSprite(id, primary, secondary)`); the default purple/gold set is generated at load. `sprite(id)` returns the default team.
- **Facings**: 5 views are drawn (S, SE, E, NE, N); SW, W and NW are mirrors. S and N are their own mirror images, so this is the minimum for 8 facings.
- **Picking**: hit boxes are tighter than the textures; units win over buildings over nodes, then front-most. `pickEntity` uses the entities drawn on the last frame.
- **Camera**: wheel zoom 0.5x-2x about the cursor, middle-drag, arrows and WASD, 6 px edge scroll, clamped to the map's screen bounds plus 96 px. WASD collides with the QWERT/ASDFG command-card hotkeys; `cameraInput.setWasd(false)` turns it off.
- **Unknown ids** never throw: sprites fall back to a magenta "?" tile, icons to a magenta "?" icon; unknown `icon.tech.*` ids get a generic scroll glyph with initials.
- Dev pages (not in the production build): `src/client/render/dev/scene.html` and `sheet.html` under `npm run dev`.
### WP5: input and selection

- **Where**: `src/client/input/`. `Match` owns one `GameInput` (`match.input`); `match.selection` is `input.selection.ids` (ascending). Selection and control groups are client state, never in the sim.
- **Selection rules** (pure functions in `selection.ts`): click selects the entity under the cursor (units over buildings over nodes); an enemy or node is selected alone for inspection and never mixed with own entities. Shift click toggles own entities. Drag box (4 px threshold) selects own units only; an empty box clears, shift adds. Double click (400 ms, same entity) selects every own entity of that kind and type currently on screen. Ids are kept ascending; entities that disappear are pruned every frame (selection and control groups).
- **Control groups**: Ctrl/Cmd+1-9 assigns (an empty selection is ignored), 1-9 recalls, pressing the same digit again within 400 ms centres the camera on the group.
- **Right click** (`contextual.ts`, table in its header): ground, unit or other building gives `move` (to the clicked point); node gives `gather` for villagers whose def can gather that kind; own unfinished building gives `assist` for builders; own completed farm gives `gather` on the farm; own drop-off gives `dropOff` for villagers carrying an accepted resource; everyone else in the selection gets `move` (to the footprint centre when the target is a node or building). Shift sets `queue: true` (not on `dropOff`/`setRally`). With only buildings selected, own completed buildings that train units get `setRally` (with `targetId` for a node or farm). Units win in a mixed selection. The gather, assist, dropOff and rally handlers may still reject in the sim; the commands are issued regardless.
- **Hotkeys** are one table (`hotkeys.ts`), matched on `KeyboardEvent.code`: command card QWERT/ASDFG/ZXCVB (slots 0-14, from `CARD_HOTKEYS`), Ctrl+1-9 / 1-9, `H` (select and centre the Town Center), `.` (cycle idle villagers: no order, queue, path or pending request), `Delete` (delete command for selected own entities), `Esc` (cancel the active input mode, else emit `menu`), `F3` (emit `toggleDebug`), `F10`/`Pause` (toggle loop pause). WASD camera panning is disabled (`cameraInput.setWasd(false)`); arrows, edge scroll and middle-drag remain. The canvas context menu is suppressed.
- **API for later packages**: `input.selection.subscribe(fn)` / `.ids` / `.set` (HUD narrowing a multi-selection); `input.onCardSlot(fn)` receives hotkey presses and `input.triggerCardSlot(slot)` fires the same path for button clicks; `input.onUiAction(fn)` receives `'menu'` and `'toggleDebug'`; `input.setMode(mode | null)` routes left/right click, pointer move and Esc to a modal handler (placement) before normal input; `input.issueContextOrder(canvasPoint, shift)` is the minimap's right click; `input.perform(action)` runs any hotkey action.
- **Temporary visuals**: `tempSelectionFeedback.ts` draws unit rings and building outlines in `layers.groundOverlays` and the drag box in `layers.worldOverlays`. WP10 replaces it (drive overlays from `input.selection` and `input.dragBox`, then delete the module).
- **Integration**: the game screen builds `createProceduralManifest({ registry })`, starts the camera on the Town Center, and `window.__game.selection` reads the real selection. `tests/unit/client/artCoverage.test.ts` asserts every real unit, building, node and tech sprite and icon id resolves to a drawing; all current data ids already do.
### WP7: construction

- **canPlace** (`rules/placement.ts`) returns the contract `PlacementResult`: per-tile `outOfBounds` / `notBuildable` (terrain) / `occupied` (occupancy grid, plus tiles covered by non-blocking buildings such as farms, which are not in the grid), the `availability` object (rule reasons, cost, affordability) and `ok`. The build limit is also enforced here (owned buildings of the type, unfinished included; a `buildLimit` reason is added if `availability` did not already report it). Units on the footprint never block placement. Unknown or non-`buildable` defs are never ok.
- **build command**: rejects in this order: unit checks (`unknownEntity`, `notOwner`, `cannotPerform` also when the unit's `builds` lacks the type), `unknownDef`, `invalidTarget` (not a buildable building), `notAvailable` (with reasons), `cannotPlace` (with the problem list), `cannotAfford` (with shortfall). On success: cost (the resolved `availability.cost`) is deducted and stored in `costPaid`, the foundation is created, `BuildingPlaced` is emitted, blocking defs are written to the occupancy grid and bump `occupancyVersion` (farms do neither), each unit gets a `build` order (`queue: true` appends, so several foundations can be queued, all paid up front), and units inside a blocking footprint are teleported to the nearest free tile centre (first ring outside the footprint with a free tile, nearest centre, ties by tile index) and lose their path.
- **Progress** is a 0-1 fraction: each tick an unfinished building adds `(1 + 0.5 (n - 1)) / buildTicks`, `buildTicks = max(1, round(buildTime * 20))` (resolved `buildTime` from the stats cache if present). `n` counts units in the `building` phase of a build/assist order on it; the list is pruned each tick. Complete at `progress >= 1 - 1e-9`, then exactly 1, `BuildingCompleted`, builder list cleared. `instantBuild` completes on the first tick with a builder.
- **Build/assist order**: walk (`followPath` to the footprint), `building` phase once in a tile adjacent to (or inside) the footprint; leaving it returns to walking. A path that ends without reaching the site gives up (`VillagerIdle`). A missing target ends the order; a finished target continues via the `replace` step: with orders queued the next one; else builders of a `dropOff`-tagged non-Town-Center building (camps, mill) gather the nearest node (to the building centre, ties by id) whose resource the building accepts, that the unit can gather and that has room; the builder of a farm gets `gather` on it if the farm is free; otherwise idle with `VillagerIdle`.
- **assist command**: own unfinished building gives `assist` (units must be able to build the type); own completed farm gives `gather` on it (units must be able to farm); anything else is `invalidTarget`.
- **cancelConstruction** acts at once (not in cleanup): full `costPaid` refund, footprint freed (+`occupancyVersion`), current build/assist orders of all units targeting it ended (queued ones are skipped when reached), entity removed. Finished or unknown targets are rejected (`invalidTarget` / `unknownEntity`).
- `availability` is WP8's; `tests/sim/construction.test.ts` mocks it with a base-cost stand-in.

### WP6: gathering

- **Files**: `systems/orders/gather.ts`, `systems/orders/dropOff.ts`, helpers in `systems/gatherTargets.ts`. The command handler table needs no change.
- **Targets**: a resource node with `amount > 0`, or a completed farm owned by the unit's owner. A target that no longer exists or is empty is "depleted".
- **Commands** (all-or-nothing, first failure wins): units via `validateOwnUnits`; `gather`: target `unknownEntity`, a unit / empty node / non-farm building `invalidTarget`, enemy farm `notOwner`, unfinished farm `notConstructed`, any unit with no base rate for the target's gather kind `cannotPerform` (so soldiers are refused). A full node is accepted; the order retargets when it begins. `dropOff` (always replaces the current order): unknown building `unknownEntity`, non-building `invalidTarget`, `notOwner`, `notConstructed`; a unit carrying nothing `cannotPerform`; a building that does not accept the carried type `invalidTarget`.
- **Loop**: phases `start` (take a slot on the target, else retarget) -> `toNode` -> `harvesting` -> `toDropOff` -> deposit -> `start`. A unit that is adjacent to the target footprint (`isAdjacentToFootprint`) harvests. Every harvesting tick adds `rate / TICK_RATE` to `harvestAccumulator`; each whole unit moves one point from the node (farms: nothing) to `carried`, never beyond capacity. Float drift is absorbed with a 1e-9 epsilon. At capacity the unit walks to the nearest completed own drop-off that accepts the resource and that it can reach (squared straight-line distance from the unit to the footprint centre, ties by lowest id), deposits into `players[owner].resources` and starts over.
- **Rate and capacity** come from `runtime.resolvedStats[owner][unitType]` when that cache has `gatherRate.<kind>` / `carryCapacity`, else the def's base value (same pattern as unit speed). It never calls `resolvedStat`, which is still a stub that throws; once WP8 fills the cache the modified values apply without a code change here.
- **Slots**: the order holds one slot (`gathererIds`, ascending) on its target from `start` until it ends, including while walking to a drop-off. `end` releases it (stop, replacing order, deletion, order finished). Node limits come from the node def (`maxGatherers`), farms from `farm.maxGatherers`.
- **Retarget** (target depleted, removed, or full): nearest node or own farm of the same resource, centre to centre from `anchor`, at most `GATHER_RETARGET_RADIUS` (8, inclusive) tiles, with a free slot, a rate for the unit and a reachable approach tile; ties by lowest id. `anchor` is moved to the new target's centre, so a long chain of trees is cleared. Berries may therefore retarget to a farm and vice versa (same resource, food). A partly filled load is kept and topped up; if nothing is found the unit first delivers a held load (if a drop-off exists), then the order finishes.
- **Idle**: when nothing is left (or no drop-off exists for a full load, or the target is unreachable) the order finishes and `VillagerIdle` is emitted if the unit has no queued order.
- **Resource switch**: beginning a gather order whose resource differs from the carried type discards the carried load.
- **Depletion**: the order only decrements `amount`; cleanup removes the node and emits `ResourceNodeDepleted`.
- **Drop-off order**: walks to the building, deposits the whole load, finishes silently. If the building vanishes or no longer accepts the load, the order finishes and the load is kept.
- **Starting a gather from elsewhere** (construction auto-continue, rally onto a resource, farm `assist`): call `assignOrder(ctx, unit, { type: 'gather', targetId }, queue)`. The target may be a node or a completed farm; the order is silently skipped if the target is invalid or the unit cannot gather it.
### WP8: production, research, ages

- **Stats** (`rules/stats.ts`): `(base + all add) * all mul` over civ bonuses then researched techs; costs rounded with `Math.round`, min 0. Cache `runtime.resolvedStats[player][def][stat]` holds every stat a def has (units: hp, attack, armor, range, speed, popCost, trainTime, plus carryCapacity and `gatherRate.<kind>` only if it gathers; buildings: hp, armor, buildTime, popProvided, incomeRate only with `income`; techs: researchTime; all: `cost.food|wood|gold|stone`). `resolvedStat` throws for a stat a def lacks, computes on the fly for a def missing from the cache. `resolvedCost(ctx, player, def)` is the helper for costs. Cache is rebuilt on tech completion and in `rebuildRuntime`.
- **Availability** (`rules/availability.ts`): hidden (`wrongCiv`, `replaced`) returns that single reason. A researched tech returns only `alreadyResearched`. Otherwise reasons are ordered: requiresAge, requiresBuilding, requiresTech, ageBuildings, buildLimit (counts foundations), researchInProgress or ageAdvanceInProgress (queued in any own building). An age advance's `age` is the age the player must be in now (`player.age >= def.age`). `ageBuildings` counts distinct completed own building types with `countsTowardAge` and `age === player.age`. It does not check `buildable` or whether a building trains the def; handlers do. Unknown def ids give `{available:false, hidden:true, reasons:[]}`.
- **Commands**: train/research check, in order: entity exists, owner, is a building, constructed, def kind (`unknownDef`), building lists it (`cannotPerform`), queue length (`queueFull`), availability (`notAvailable` + reasons), affordability (`cannotAfford` + shortfall). `cancelQueue` refunds the item's `costPaid`. `setRally` is all-or-nothing, needs buildings that train units, a point inside the map, and an existing `targetId`.
- **Production**: one item completes per building per tick; the head gains one tick per step, so an item queued in step N with `ticksTotal = T` completes in step N+T-1. `instantResearch` completes the head on its first tick (units too). A unit spawns when `living popCost + its popCost <= popCap` (items queued elsewhere do not reserve room); otherwise it holds at 100%, `PopulationCapped` once. `popCap`/`popUsed` are recomputed at the start of production, on enqueue/cancel/spawn and in cleanup.
- **Spawn and rally**: candidate tiles are the 8-connected ring around the footprint (then rings 2 and 3 if full) that are free in `occupancy`; the one nearest (squared distance from tile centre) to the rally point wins, ties by tile index. The rally point is the target entity's footprint centre when `targetId` still exists, else the stored x,y. Without a rally the unit appears on the south side. Rally to a node/own farm the unit can gather gives `{type:'gather', targetId}`; anything else gives `{type:'move', x, y}`; both through `assignOrder(..., queue=false)`.
- **Income**: accumulator is snapped to a 1e-9 grid after each add so 0.25 gold/s pays exactly one gold per 80 ticks (125 in 10,000 ticks).
- **Objectives**: `completedTick` and the event's `tick` are `state.tick + 1` (ticks elapsed including the completing one).
