# Design: rules as implemented

This file records the game rules as they actually work in code. `docs/PLAN.md` is the intent; when implementation differs or a rule is clarified, update this file in the same change.

## Status

Phases 0 to 2 are integrated: the sim implements the economy (gathering, construction, production, research, ages, passive income, objective), the HUD, minimap and placement are wired to it, and the plan 9.3 scenarios run through the real UI (see "Phase 2 integration" at the end). The headless economy bot and its balance pass (WP11), replay, save validation and performance work (WP12) and the UX pass (WP13) are done too (see their sections); Combat is the one part of the plan not implemented yet: units have attack stats but nothing fights.

## Contract decisions made in Phase 0

- **Build command places the foundation immediately.** When a `build` command is applied, the sim validates with `canPlace`, deducts the cost, creates the foundation and gives each unit a `build` order referencing it. `assist` on an unfinished building behaves the same as `build`; `assist` on a completed farm becomes a `gather` order on it.
- **Farms are buildings** with a `farm` ability; `gather` orders target either a resource node or a completed farm building.
- **Path requests are atomic.** A request is started only while budget remains and always completes within the tick, so no partial A* state is saved. The queue (`state.pathQueue`) and `occupancyVersion` are in state so save/load continues identically.
- **Cheats are commands** (`type: 'cheat'`) and cheat flags live in `PlayerState.cheats`, so replays and saves stay exact. The client only exposes them in dev/e2e builds.
- **Production timing**: each queue item stores integer `ticksDone`/`ticksTotal`; `ticksTotal = max(1, round(seconds * TICK_RATE))` fixed at enqueue. Construction progress is a float in [0, 1] (multi-builder speed is fractional), clamped to exactly 1 on completion.
- **Modifier selection**: a modifier matches a def if the def's id is in `select.ids` OR the def has any tag in `select.tags`. Resolution: base, then civ, then tech modifiers; all `add` before all `mul`. Resolved costs are rounded with `Math.round`.
- **Player ids** equal their index in `players`; 0 is the neutral owner of resource nodes (`civ: null`), real players are 1..n.
- **Save format**: canonical JSON of `{ version, state }`; unknown versions are refused. (M2: version 2 adds `controllers`, see below.)

## M2 contract decisions (Phase 0, WP20)

Milestone 2 (`docs/PLAN-M2.md`) adds combat and a computer opponent. Phase 0 wrote the contracts (PLAN-M2 section 3) with stub systems; nothing behaves differently from M1 until the Phase 1 packages land (an M1-field projection of 1- and 2-player economy-bot games is byte-identical to M1 over 12,000 ticks, and the economy bot timings are unchanged).

- **Tick order** (PLAN-M2 2.2, `sim.ts`): commands; production; income; acquisition (rebuilds the spatial index); orders; path queue; movement; unit attacks (8a) and building attacks (8b); projectiles; construction (incl. construction hp and repair); death, then cleanup; outcome, then objectives; `tick++`. Stubs (marked `STUB`/`TODO(WPnn)`): `runAcquisition` (rebuilds the stub index, resets the budget), `runUnitAttacks`, `runBuildingAttacks`, `runDeath`, `runOutcome` (no-ops), `runProjectiles` (decrements `ticksLeft` and drops spent projectiles only).
- **Real in Phase 0:** `computeDamage`, `applyDamage`, `isEnemy`, `distSqToTarget`, `unitCombat`/`buildingCombat` (`systems/combat/damage.ts`), `spawnProjectile`, `recordStat` (`systems/matchStats.ts`) and its calls (production spawn: `unitsTrained`; construction complete: `buildingsBuilt`; `depositCarried` and passive income: `resourcesGathered`; research complete: `techsResearched`, `ageReachedTick`; population recompute: `peakPopulation`), entity defaults, `GameConfig` defaults, the 4.11 construction-hp update (`updateConstructionHp`, owned by WP24 from here) and the `setHp`/`defeat`/`spawnUnit owner` cheats.
- **Combat stats** are `StatKey`s `hp`, `attack`, `meleeArmor`, `pierceArmor`, `range` (`armor` is gone), rounded with `Math.round` after resolution like costs; buildings with `combat.attack` also resolve `attack` and `range`. `runtime.combat[player][defId]` holds the resolved profiles (ticks: `windupTicks = max(1, round(windup*20))`, `cooldownTicks = max(windupTicks+1, round(cooldown*20))`; `reach = range + CombatRules.reach`) and is rebuilt with `resolvedStats` (`rules/stats.ts`). `ResolvedBuildingCombat` carries `bonusResist: 0` so it can be the defender in `computeDamage`.
- **`applyDamage`**: `hp` clamps at 0; `lastAttackerId` is set only while the target had hp > 0; `lastDamagedTick = state.tick`; an enemy hit emits `UnderAttack` (anchor: unit position or footprint centre) when the owner has no alert, the last one is at least 100 ticks old, or the hit is at least 12 tiles from it, and stores `player.alert`; an idle (no order, no queue), aggressive unit with `autoAcquire` gets `nextScanTick = tick + 1`.
- **Entity defaults**: units start at full (resolved) hp, `aggressive`, `combat = { cooldown 0, windup 0, swingTargetId null, nextScanTick tick + id % 10, lastAttackTick null }`. Buildings: foundations `hp = builtHp = max(1, floor(maxHp * 10 / 100))`, completed (starting Town Center) at max; `attack` non-null exactly for defs with `combat.attack` (`nextScanTick` staggered like units); repair fields zero. `createUnit`/`createBuilding` keep their M1 leading parameters and gain optional `maxHp` (and `data` for buildings), defaulting to the base hp and the game registry.
- **Players and matches**: `GameConfig.players[i]` (`PlayerConfig`) may set `color`, `controller`, `difficulty`, `name`. Defaults: colour `PLAYER_COLORS[slot]` (slot 0 blue, slot 1 red; no longer the civ's purple), controller `human` for slot 0 and `ai` for other slots with a difficulty, an AI slot without a difficulty plays `standard`, names `Player`, `Player N`, `Computer (Easy|Standard|Hard)`, neutral player 0 `Neutral`. Mode: `conquest` with exactly two players, else `sandbox`; conquest players get objective `conquest:<id>` (`targetAge: null`), sandbox players the M1 `reachEmpireAge:<id>`. `ageReachedTick[age-1]` is `state.tick + 1` of the completing tick, like objectives.
- **Commands**: the new commands are shape-checked in `isCommandShapeValid` and their handlers are stubs rejecting `invalidCommand` (attack, attackMove, hold, setStance: WP21; repair: WP24; resign: WP23). The order handlers for `attack`, `attackMove`, `hold`, `repair` are stubs whose `begin` returns null. A command (other than `cheat`) from a player whose `outcome` is `defeated` is rejected with `playerDefeated`; the winner (`won`) keeps playing.
- **Cheats**: `spawnUnit.owner` (default: the issuer) spawns for any real player; `setHp` sets any unit's or building's hp (rounded, clamped to 0..max; nodes `invalidTarget`); `defeat` sets `outcome = 'defeated'`, `defeatedTick = tick + 1` and emits `PlayerDefeated{conquered}` (again on a non-playing player: `invalidTarget`); destroying the player's entities is the outcome step's job (WP23).
- **Data** (PLAN-M2 5): section 5.1/5.2 combat numbers, `src/data/combat.ts` (`CombatRules`), the Town Center buildable (275 wood, 100 stone, 150 s, economy menu, in `villager.builds`), the 12 military upgrades (`militaryTech`, level II requires level I) in the Barracks, Archery Range and Stable research lists.
- **Save v2**: canonical JSON of `{ version: 2, state, controllers }`, controllers sorted by player id. `deserializeSave` returns `{ sim, controllers }` (v1 files: `[]`); `deserialize` returns the sim only (a damaged controllers block is still refused). `MIGRATIONS[1]` (state, data) upgrades v1 states as PLAN-M2 3.6 says (v1 buildings had no hp: `hp = builtHp`); anything a migration throws on a damaged file becomes `corrupt`. Validation adds the M2 player fields, match, objectives per kind, projectiles (ascending ids below `nextProjectileId`, kinds, flight ticks, finite vectors, damage), unit and building combat fields, `repairerIds` naming units, attack state present exactly for attacking defs, and hp/builtHp within the resolved max (checked once the runtime exists). Fixtures: `save-v1.json` (frozen), `save-v1-as-v2.json`, `save-v2.json` (built by hand in `tests/sim/m2fixtures.ts`; regenerate with `UPDATE_SAVE_FIXTURE=1 npx vitest run tests/sim/m2contracts.test.ts`).
- **Public API**: `src/sim/index.ts` also exports `deserializeSave`, `ControllerSave`, `LoadedSave`, `createRng`, `rngInt`, `rngRange`. `src/bot` exports the `Controller` interface (`update(sim)`, `save()`) and an `AiPlayer` stub (`create`, `restore`, `update` returns `[]`); `EconomyBot` implements `Controller` with `save()` null.
- **Spatial index**: `runtime.spatial` is created empty for the map (`createSpatialIndex`); the query stubs (`visitUnitsNear`, `visitBuildingsNear`) scan entities in ascending id with the contract's budget and stop rules until WP21's grid lands. `directPath` returns false (callers fall back to `followPath`).
- **Client contracts**: `AssetManifest.teamSprite` (promoted from `TeamAssetManifest`), `UnitAnimState` gains `attack` and `death` (with `UNIT_STATE_FALLBACK`), `SpriteAnimation.loop`/`hitFrame`; `WorldRendererApi.pushEvents` (no-op; `Match.tick` feeds it every tick's events) and `effectStats()` (zeros); the HUD view-model fields of PLAN-M2 3.8 with neutral values (`idleMilitary` 0, `playerColor` the player's colour, `ownerName`, `combat`/`stance` null, `repairing` false, `endScreen` null, `resignConfirmOpen` false; `hp` keeps its M1 values until WP29); `REJECT_TEXT.playerDefeated`. Debug hook: `localPlayerId`, `match()`, `cheat.spawnUnit/setHp/defeat` and `effects()` work; `ai`, `startBattle`, `endScreen`, `alerts`, `cursor` throw "not implemented" until WP30.
- **Determinism lint** covers `src/bot/**` as well as `src/sim/**` (no violations existed).
- **Long tests**: files named `*.long.test.ts` are excluded from `npm test` and run with `npm run test:long` (`vitest.long.config.ts`).

## WP1 (sim core) rules

- **Command intake.** Commands sort by `(playerId, seq)` (stable). A command is dropped with `CommandRejected('invalidCommand')` before dispatch if its type is unknown, `playerId` is not a real player (1..n), `seq` is not an integer, a number is not finite, an id is not a positive integer, an id list is empty, or a required string/flag is missing. Rule checks (ownership, cost, placement) belong to the handlers.
- **Map generation.** Defs are found through the registry: the Town Center is `start.centerBuilding`; node defs are chosen by `gatherKind` (`wood`, `berries`, `gold`, `stone`), not by id. A kind with no def is skipped. Attempt k uses `rng = createRng(seed + k)`; `state.mapSeed` is the final seed (up to 24 attempts, then the last map is kept).
- **Start positions.** One player: a corner start chosen by the seed; two players: opposite corners. Each start gets 0..8 tiles of inward jitter. Edge distance is `min(25, floor(size / 4))` (25 on the 120 map), measured to the Town Center centre.
- **Clear radius.** Nothing is generated within 8 tiles of a Town Center centre except the two guaranteed berry patches, which the plan places at 6 to 10 tiles. Gold (10 to 14), stone (12 to 16) and the three tree stands (8 to 14) are outside it. Distances are node centre to Town Center centre.
- **Clusters.** Berries: 3x2 or 2x3 block; gold: 2x2 block of deposits; stone: L of three deposits; tree stands and forests: seeded blobs. Different clusters are separated by at least one free tile, and every blob tile keeps an open edge neighbour. Forests keep 15 tiles from starts and cover about 12% of tiles. Extra gold, stone and berry clusters (4, 3, 4 on 120x120, scaled by area) keep 20 tiles from starts and 14 from each other.
- **Validation.** 4-connected flood fill from the first Town Center must reach at least 95% of free walkable tiles; every Town Center, starting unit and guaranteed node must have a reachable edge-adjacent tile.
- **Starting units** stand on the ring of tiles around the Town Center, evenly spaced from a seeded offset, facing 1.
- **Delete.** All-or-nothing per command: unknown id gives `unknownEntity`, a foreign or neutral id gives `notOwner`. Unfinished buildings refund `costPaid` immediately; removal itself happens in cleanup.
- **Cleanup.** Removes depleted nodes (`amount <= 0`) and `pendingRemoval`, emits `ResourceNodeDepleted`, calls `endCurrentOrder` for removed units, clears their gatherer/builder slots and path requests, frees blocking footprints and bumps `occupancyVersion`. Orders of surviving units that point at a removed entity are not touched: order handlers treat a missing target as retarget-or-finish.
- **Queries.** `entitiesInRect` and `entityAtPoint` use half-open footprints `[tx, tx+size)`; units use `UNIT_PICK_RADIUS` (rect test: distance from the unit to the rect).
- **spawnUnit cheat** creates the unit at the exact point; rejects unknown unit types (`unknownDef`) and out-of-map or blocked tiles (`invalidTarget`).
### WP2: pathfinding and movement

- **A\***: 8-connected, integer costs 10 straight / 14 diagonal, octile heuristic to the goal rectangle. A diagonal step needs both orthogonal tiles walkable (no corner cutting). Open-list ties: lowest f, then lowest h, then lowest tile index. Walkable = in bounds and `runtime.occupancy` is 0 (terrain walkability is not consulted; M1 is all grass).
- **Goals**: a `point` goal is the tile containing the (clamped) point; a `footprint` goal is any tile in the 8-connected ring around the footprint, corners included.
- **Unreachable goal**: the path leads to the expanded tile with the lowest octile distance to the goal, ties by lowest path cost, then lowest tile index.
- **Blocked start** (unit standing on a fresh foundation): the search starts from the nearest walkable tile (squared distance, ties by tile index) and the unit walks there first.
- **Smoothing**: greedy string pulling over the A* tiles; a segment is kept only if an integer supercover walk between tile centres touches only walkable tiles, and a segment passing exactly through a tile corner also needs both side tiles walkable. Waypoints are tile centres without the start tile; a reached `point` goal ends at the exact point.
- **Request queue**: FIFO, budget `PATH_BUDGET_PER_TICK` expanded nodes per tick. Each search is capped at the remaining budget; if it would exceed it, its result is discarded and the request stays at the head of the queue for the next tick (a discarded search's expansions still count, so a tick never exceeds the budget). The first search of a tick runs with the full budget and is always used (if it is still capped, its best partial path is used; impossible on 120x120). The search starts from the unit's current tile (it stood still while waiting).
- **Following**: walking orders call `followPath(ctx, unit, goal)` every tick (`path/follow.ts`). When `occupancyVersion` changed since the path was computed, all remaining segments are re-checked; if any is blocked a new path is requested, otherwise the path's version is refreshed. Movement also stops a unit whose next segment became blocked.
- **Approach tile**: walkable ring tile in the same connected component as the origin's tile (any walkable ring tile if the origin's tile is blocked, e.g. a building centre), nearest by squared distance from the origin to the tile centre, ties by tile index; `null` if none.
- **Group move slots**: walkable tiles ordered by squared tile distance from the clicked tile, ties by tile index, restricted to the clicked tile's component when that tile is walkable. Slot 0 is the exact clicked point when its tile is walkable, others are tile centres. Units sorted by squared distance to the clicked point (ties by id) take slots in order, so the nearest unit gets the clicked point. Slots repeat only if the component is smaller than the group.
- **Commands**: `move` and `stop` are all-or-nothing: any unknown id rejects with `unknownEntity`, a foreign id with `notOwner`, a non-unit with `cannotPerform` (first failing id in ascending order); `move` with non-finite coordinates rejects with `invalidCommand`. Duplicate ids are ignored.
- **Movement**: speed = resolved `speed` stat from the runtime cache, else the unit def, else 1 tile/s; a unit may pass several waypoints in one tick. Facing comes from the tick's displacement: a component counts when it exceeds 0.4x the other (octant boundary ~22 degrees).
- **Separation**: only idle units (no order, empty queue, no path, no pending request). Pairs closer than `SEPARATION_RADIUS` each move half the overlap apart (coincident units split along one of 8 directions picked by `higherId % 8`); pushes are summed then applied, and a push ending on a blocked tile is skipped. Pairs are found with a per-tick tile hash (scratch, not state).
## WP3: renderer and placeholder art

- **Layers** (all in world-pixel space, moving with the camera, back to front): `terrain` (16x16-tile baked chunks, at most 30 live, off-screen ones hidden), `groundOverlays` (WP10: selection rings, outlines, placement tiles, rally lines, order markers), `entities` (depth sorted), `worldOverlays` (WP10: progress bars, carried-resource dots, rally flags, placement label, drag box). Exposed as `renderer.layers`.
- **Depth**: sprites sort by `x + y` of the anchor (unit interpolated position, footprint centre for buildings and nodes), ties by id. Footprints and sprite ids come from `registry.def(typeId)` and fall back to `DEFAULT_FOOTPRINT` / `'<kind>.<typeId>'` when a def is missing.
- **Animation state** is derived from the unit: moving (pos differs from prevPos, or a path is being followed) is `walk`, or `carry` when carrying; gather `harvesting` and build/assist `building` phases are `work`; otherwise `idle`. Buildings under construction show `foundation` below 30% progress, `scaffold` after.
- **Team colour**: sprites are generated per team colour on demand (`teamSprite(id, primary, secondary)`); the default purple/gold set is generated at load. `sprite(id)` returns the default team.
- **Facings**: 5 views are drawn (S, SE, E, NE, N); SW, W and NW are mirrors. S and N are their own mirror images, so this is the minimum for 8 facings.
- **Picking**: hit boxes are tighter than the textures; units win over buildings over nodes, then front-most. `pickEntity` uses the entities drawn on the last frame.
- **Camera**: wheel zoom 0.5x-2x about the cursor, middle-drag, arrows and WASD, 6 px edge scroll, clamped to the map's screen bounds plus 96 px. WASD collides with the QWERT/ASDFG command-card hotkeys; `cameraInput.setWasd(false)` turns it off.
- **Unknown ids** never throw: sprites fall back to a magenta "?" tile, icons to a magenta "?" icon; unknown `icon.tech.*` ids get a generic scroll glyph with initials.
- Dev pages (not in the production build): `src/client/render/dev/scene.html` and `sheet.html` under `npm run dev`.
### WP5: input and selection

- **Where**: `src/client/input/`. `Match` owns one `GameInput` (`match.input`); `match.selection` is `input.selection.ids` (ascending). Selection and control groups are client state, never in the sim.
- **Selection rules** (pure functions in `selection.ts`): click selects the entity under the cursor (units over buildings over nodes); an enemy or node is selected alone for inspection and never mixed with own entities. Shift click toggles own entities. Drag box (4 px threshold) selects own units only; an empty box clears, shift adds. Double click (400 ms, same entity) selects every own entity of that kind and type currently on screen. Ids are kept ascending; entities that disappear are pruned every frame (selection and control groups).
- **Control groups**: Ctrl/Cmd+1-9 assigns (an empty selection is ignored), 1-9 recalls, pressing the same digit again within 400 ms centres the camera on the group.
- **Right click** (`contextual.ts`, table in its header): ground, unit or other building gives `move` (to the clicked point); node gives `gather` for villagers whose def can gather that kind; own unfinished building gives `assist` for builders; own completed farm gives `gather` on the farm; own drop-off gives `dropOff` for villagers carrying an accepted resource; everyone else in the selection gets `move` (to the footprint centre when the target is a node or building). Shift sets `queue: true` (not on `dropOff`/`setRally`). With only buildings selected, own completed buildings that train units get `setRally` (with `targetId` for a node or farm). Units win in a mixed selection. The gather, assist, dropOff and rally handlers may still reject in the sim; the commands are issued regardless.
- **Hotkeys** are one table (`hotkeys.ts`), matched on `KeyboardEvent.code`: command card QWERT/ASDFG/ZXCVB (slots 0-14, from `CARD_HOTKEYS`), Ctrl+1-9 / 1-9, `H` (select and centre the Town Center), `.` (cycle idle villagers: no order, queue, path or pending request), `Delete` (delete command for selected own entities), `Esc` (cancel the active input mode, else emit `menu`), `F3` (emit `toggleDebug`), `F10`/`Pause` (toggle loop pause). WASD camera panning is disabled (`cameraInput.setWasd(false)`); arrows, edge scroll and middle-drag remain. The canvas context menu is suppressed.
- **API for later packages**: `input.selection.subscribe(fn)` / `.ids` / `.set` (HUD narrowing a multi-selection); `input.onCardSlot(fn)` receives hotkey presses and `input.triggerCardSlot(slot)` fires the same path for button clicks; `input.onUiAction(fn)` receives `'menu'` and `'toggleDebug'`; `input.setMode(mode | null)` routes left/right click, pointer move and Esc to a modal handler (placement) before normal input; `input.issueContextOrder(canvasPoint, shift)` is the minimap's right click; `input.perform(action)` runs any hotkey action.
- **Visuals**: selection rings, building outlines and the drag box are drawn by the WP10 overlays (`render/overlays`); `tempSelectionFeedback.ts` was deleted.
- **Integration**: the game screen builds `createProceduralManifest({ registry })`, starts the camera on the Town Center, and `window.__game.selection` reads the real selection. `tests/unit/client/artCoverage.test.ts` asserts every real unit, building, node and tech sprite and icon id resolves to a drawing; all current data ids already do.
### WP7: construction

- **canPlace** (`rules/placement.ts`) returns the contract `PlacementResult`: per-tile `outOfBounds` / `notBuildable` (terrain) / `occupied` (occupancy grid, plus tiles covered by non-blocking buildings such as farms, which are not in the grid), the `availability` object (rule reasons, cost, affordability) and `ok`. The build limit is also enforced here (owned buildings of the type, unfinished included; a `buildLimit` reason is added if `availability` did not already report it). Units on the footprint never block placement. Unknown or non-`buildable` defs are never ok.
- **build command**: rejects in this order: unit checks (`unknownEntity`, `notOwner`, `cannotPerform` also when the unit's `builds` lacks the type), `unknownDef`, `invalidTarget` (not a buildable building), `notAvailable` (with reasons), `cannotPlace` (with the problem list), `cannotAfford` (with shortfall). On success: cost (the resolved `availability.cost`) is deducted and stored in `costPaid`, the foundation is created, `BuildingPlaced` is emitted, blocking defs are written to the occupancy grid and bump `occupancyVersion` (farms do neither), each unit gets a `build` order (`queue: true` appends, so several foundations can be queued, all paid up front), and units inside a blocking footprint are teleported to the nearest free tile centre (first ring outside the footprint with a free tile, nearest centre, ties by tile index) and lose their path.
- **Progress** is a 0-1 fraction: each tick an unfinished building adds `(1 + 0.5 (n - 1)) / buildTicks`, `buildTicks = max(1, round(buildTime * 20))` (resolved `buildTime` from the stats cache if present). `n` counts units in the `building` phase of a build/assist order on it; the list is pruned each tick. Complete at `progress >= 1 - 1e-9`, then exactly 1, `BuildingCompleted`, builder list cleared. `instantBuild` completes on the first tick with a builder.
- **Build/assist order**: walk (`followPath` to the footprint), `building` phase once in a tile adjacent to (or inside) the footprint; leaving it returns to walking. A path that ends without reaching the site gives up (`VillagerIdle`). A missing target ends the order; a finished target continues via the `replace` step: with orders queued the next one; else builders of a `dropOff`-tagged non-Town-Center building (camps, mill) gather the nearest node (to the building centre, ties by id) whose resource the building accepts, that the unit can gather and that has room; the builder of a farm gets `gather` on it if the farm is free; otherwise idle with `VillagerIdle`.
- **assist command**: own unfinished building gives `assist` (units must be able to build the type); own completed farm gives `gather` on it (units must be able to farm); anything else is `invalidTarget`.
- **cancelConstruction** acts at once (not in cleanup): full `costPaid` refund, footprint freed (+`occupancyVersion`), current build/assist orders of all units targeting it ended (queued ones are skipped when reached), entity removed. Finished or unknown targets are rejected (`invalidTarget` / `unknownEntity`).
- `availability` is WP8's; `tests/sim/construction.test.ts` mocks it with a base-cost stand-in.

### WP6: gathering

- **Files**: `systems/orders/gather.ts`, `systems/orders/dropOff.ts`, helpers in `systems/gatherTargets.ts`. The command handler table needs no change.
- **Targets**: a resource node with `amount > 0`, or a completed farm owned by the unit's owner. A target that no longer exists or is empty is "depleted".
- **Commands** (all-or-nothing, first failure wins): units via `validateOwnUnits`; `gather`: target `unknownEntity`, a unit / empty node / non-farm building `invalidTarget`, enemy farm `notOwner`, unfinished farm `notConstructed`, any unit with no base rate for the target's gather kind `cannotPerform` (so soldiers are refused). A full node is accepted; the order retargets when it begins. `dropOff` (always replaces the current order): unknown building `unknownEntity`, non-building `invalidTarget`, `notOwner`, `notConstructed`; a unit carrying nothing `cannotPerform`; a building that does not accept the carried type `invalidTarget`.
- **Loop**: phases `start` (take a slot on the target, else retarget) -> `toNode` -> `harvesting` -> `toDropOff` -> deposit -> `start`. A unit that is adjacent to the target footprint (`isAdjacentToFootprint`) harvests. Every harvesting tick adds `rate / TICK_RATE` to `harvestAccumulator`; each whole unit moves one point from the node (farms: nothing) to `carried`, never beyond capacity. Float drift is absorbed with a 1e-9 epsilon. At capacity the unit walks to the nearest completed own drop-off that accepts the resource and that it can reach (squared straight-line distance from the unit to the footprint centre, ties by lowest id), deposits into `players[owner].resources` and starts over.
- **Rate and capacity** come from `runtime.resolvedStats[owner][unitType]` when that cache has `gatherRate.<kind>` / `carryCapacity`, else the def's base value (same pattern as unit speed). It does not call `resolvedStat`; `rebuildRuntime` fills the cache (new game, load, every tech completion), so researched modifiers (Iron Axes, Hand Carts) apply.
- **Slots**: the order holds one slot (`gathererIds`, ascending) on its target from `start` until it ends, including while walking to a drop-off. `end` releases it (stop, replacing order, deletion, order finished). Node limits come from the node def (`maxGatherers`), farms from `farm.maxGatherers`.
- **Retarget** (target depleted, removed, or full): nearest node or own farm of the same resource, centre to centre from `anchor`, at most `GATHER_RETARGET_RADIUS` (8, inclusive) tiles, with a free slot, a rate for the unit and a reachable approach tile; ties by lowest id. `anchor` is moved to the new target's centre, so a long chain of trees is cleared. Berries may therefore retarget to a farm and vice versa (same resource, food). A partly filled load is kept and topped up; if nothing is found the unit first delivers a held load (if a drop-off exists), then the order finishes.
- **Idle**: when nothing is left (or no drop-off exists for a full load, or the target is unreachable) the order finishes and `VillagerIdle` is emitted if the unit has no queued order.
- **Resource switch**: beginning a gather order whose resource differs from the carried type discards the carried load.
- **Depletion**: the order only decrements `amount`; cleanup removes the node and emits `ResourceNodeDepleted`.
- **Drop-off order**: walks to the building, deposits the whole load, finishes silently. If the building vanishes or no longer accepts the load, the order finishes and the load is kept.
- **Starting a gather from elsewhere** (construction auto-continue, rally onto a resource, farm `assist`): call `assignOrder(ctx, unit, { type: 'gather', targetId }, queue)`. The target may be a node or a completed farm; the order is silently skipped if the target is invalid or the unit cannot gather it.
### WP8: production, research, ages

- **Stats** (`rules/stats.ts`): `(base + all add) * all mul` over civ bonuses then researched techs; costs rounded with `Math.round`, min 0. Cache `runtime.resolvedStats[player][def][stat]` holds every stat a def has (units: hp, attack, armor, range, speed, popCost, trainTime, plus carryCapacity and `gatherRate.<kind>` only if it gathers; buildings: hp, armor, buildTime, popProvided, incomeRate only with `income`; techs: researchTime; all: `cost.food|wood|gold|stone`). `resolvedStat` throws for a stat a def lacks, computes on the fly for a def missing from the cache. `resolvedCost(ctx, player, def)` is the helper for costs. Cache is rebuilt on tech completion and in `rebuildRuntime`.
- **Availability** (`rules/availability.ts`): hidden (`wrongCiv`, `replaced`) returns that single reason. A researched tech returns only `alreadyResearched`. Otherwise reasons are ordered: requiresAge, requiresBuilding, requiresTech, ageBuildings, buildLimit (counts foundations), researchInProgress or ageAdvanceInProgress (queued in any own building). An age advance's `age` is the age the player must be in now (`player.age >= def.age`). `ageBuildings` counts distinct completed own building types with `countsTowardAge` and `age === player.age`. It does not check `buildable` or whether a building trains the def; handlers do. Unknown def ids give `{available:false, hidden:true, reasons:[]}`.
- **Commands**: train/research check, in order: entity exists, owner, is a building, constructed, def kind (`unknownDef`), building lists it (`cannotPerform`), queue length (`queueFull`), availability (`notAvailable` + reasons), affordability (`cannotAfford` + shortfall). `cancelQueue` refunds the item's `costPaid`. `setRally` is all-or-nothing, needs buildings that train units, a point inside the map, and an existing `targetId`.
- **Production**: one item completes per building per tick; the head gains one tick per step, so an item queued in step N with `ticksTotal = T` completes in step N+T-1. `instantResearch` completes the head on its first tick (units too). A unit spawns when `popUsed + its popCost <= popCap` where `popUsed` counts living units only (WP13; items in queues do not count, in ascending building id so simultaneous finishers cannot both exceed the cap); otherwise it holds at 100%, `PopulationCapped` once. `popCap`/`popUsed` are recomputed at the start of production, on enqueue/cancel/spawn and in cleanup.
- **Spawn and rally**: candidate tiles are the 8-connected ring around the footprint (then rings 2 and 3 if full) that are free in `occupancy`; the one nearest (squared distance from tile centre) to the rally point wins, ties by tile index. The rally point is the target entity's footprint centre when `targetId` still exists, else the stored x,y. Without a rally the unit appears on the south side. Rally to a node/own farm the unit can gather gives `{type:'gather', targetId}`; anything else gives `{type:'move', x, y}`; both through `assignOrder(..., queue=false)`.
- **Income**: accumulator is snapped to a 1e-9 grid after each add so 0.25 gold/s pays exactly one gold per 80 ticks (125 in 10,000 ticks).
- **Objectives**: `completedTick` and the event's `tick` are `state.tick + 1` (ticks elapsed including the completing one).
### WP9: HUD and menus

- **Where**: `src/client/ui/` (view-model builder, controller, components, `hud.css`) and the screens in `src/client/app/screens/`. Dev page (not in the production build): `src/client/ui/dev/hud.html` shows the real HUD over a fixture state with a fake `availability`; `scripts/wp9-screenshots.mjs` captures `docs/screenshots/wp9/`.
- **Data flow**: `buildHudViewModel` (pure; sim state + selection + client state + `HudQueries`, a subset of `SimQuery`) -> `HudController` (client state, 10 Hz refresh via `setInterval`, immediate refresh on selection change, page change and sim events) -> Preact components that render only from the view-model. Components never read sim state.
- **`HudViewModel` additions** (additive): `TopBarVM.ageIcon`, `CommandCardVM.title`, `BannerVM.id`.
- **Command card**: each selected own entity contributes its items and a mixed selection shows the intersection (villager + spearman: Stop; unit + building: nothing). Fixed slots: Economy 0 (Q), Military 1 (W), Stop 2 (E); Back, Set Rally and Cancel construction are in slot 14 (B). Units, techs and build items fill the other slots in data order unless the def has `cardSlot`. A villager page other than `main` is shown only when every selected unit builds; any selection change returns to `main`. Items with `availability(...).hidden` (or a def whose `civs` excludes the civ) never appear. Everything else appears; `enabled` is `availability.available` (rules only), unaffordable costs are `shortfall > 0` and drawn red, so clicking an affordable-rules item you cannot pay still sends the command and the sim's `cannotAfford` rejection becomes the "Not enough wood" toast. Clicking a greyed item sends nothing and toasts the first unmet requirement. Costs are `availability.cost`; time is the sim's `resolvedStat`. A tech the player already has is not shown at all (plan 4.7: it disappears from the card).
- **Commands**: train and research go to the selected completed building that offers the item with the shortest queue (ties: lowest id); Stop sends the selected units; Cancel sends `cancelConstruction` for each unfinished selected building; queue items send `cancelQueue`. Hotkeys and clicks share one path (`input.onCardSlot`; clicks call `input.triggerCardSlot`).
- **Notifications**: `NotificationCenter` (injected clock). `CommandRejected` text comes from `REJECT_TEXT` (a `Record<RejectReason, string>`, so a new reason fails to compile until it has text); `cannotAfford` names every short resource and `notAvailable` uses the first unmet requirement. `PopulationCapped` toasts "Build more houses". Completed buildings and research toast; villager training does not (only other units); idle villagers merge into one toast per batch. At most 4 show, 4 s each; the toast rules are under WP13 (merging, routine toasts). `AgeAdvanced` and `ObjectiveCompleted` are banners (5 s each, queued one at a time); the objective subtitle includes the elapsed game time (`tick / TICK_RATE`).
- **Menus and saves**: Esc (`input.onUiAction('menu')`) toggles the in-match menu and pauses the loop while it is open (an existing pause is kept). Save/Load use `SaveStorage` (named slots `save-<ms>`), plus export to and import from a file. `parseSave` classifies failures: an unsupported `version` reads "This save is from a different version of the game (save version N; this game reads version 1) and cannot be loaded."; a `version` that is not a whole number (`"1"`, `null`, `1.5`) reads "This save has an unrecognised version (...) and cannot be loaded.". Restart rebuilds from the match's config (`configFromSim` for loaded saves).
- **App changes**: New Game now goes through civilization select (the e2e specs click `start-match` after `new-game`). The art manifest is created once by `AppHost.loadManifest()` (started at boot, awaited by the loading screen with a progress bar) and shared by menus and matches; it is no longer destroyed per match. `GameScreen` takes optional `GameHooks` (`onStartPlacement`, `onStartRally`, `onMatchReady`) that default to nothing.
- **Pointer events**: `.hud` never captures them; only `.panel` elements do. The bottom row is minimap frame (`#minimap-slot`, where the WP10 minimap is mounted; it shows a "Minimap" label only until then), selection panel, command card.

## WP10: minimap, overlays and placement

- **Overlays** (`src/client/render/overlays/`, `WorldOverlays`, built by `Match`, `update()` after every `renderer.render`): selection ring on selected units (own green, other red), footprint outline on selected buildings (own green, enemy red) and nodes (yellow), drag box, bars over own buildings (orange construction progress; blue front-of-queue progress, training or research), a colour-coded dot above own villagers that carry something, a flag and thin line for each selected own building with a rally point, and a 750 ms fading ring where a `move`, `gather`, `assist` or `build` was just issued (`CommandBuffer.onIssue` feeds it; at most 8 live, oldest replaced). Everything is a pooled sprite with baked textures; a steady-state frame only writes sprite properties. Only entities drawn last frame (`renderer.lastDrawn`, already culled) plus the selected buildings' rally points are visited. Bars sit above the footprint centre (28 px per footprint tile plus 24) (not the sprite top, which has padding) and keep a constant screen size. `overlays.stats` counts what was drawn (tests).
- **Placement mode** (`src/client/input/placement/`): `createPlacementMode(type, deps)` is an `InputMode`. The footprint is centred under the cursor: top-left tile = `round(world - size/2)` per axis (odd sizes centre on a tile, even sizes on a corner). `canPlace` (injected; the controller passes `sim.query.canPlace`) drives the ghost: per-tile green/red fill, overall footprint outline tint, the building art at 55% alpha, and a reason label for invalid spots (`describePlacementProblem`: outside the map, blocked, terrain, then availability reasons, then "Not enough <resource>"). Left click on a valid spot issues `build` for the selected own units whose def lists the type in `builds`, with `queue = shift`; without Shift the mode ends, with Shift it stays. An invalid click, or no builder selected, is consumed, issues nothing and calls `onInvalid(text)` (HUD toast). Right click and Esc cancel (Esc is consumed, it does not open the menu). The ghost hides while the pointer is outside the canvas.
- **Rally mode**: `createRallyMode(deps)`: the next left click issues `setRally` for the selected own buildings that train units; a node or building under the cursor becomes an entity rally (`targetId`, point = footprint centre), a unit or ground is a ground rally clamped into the map. Right click and Esc cancel.
- **Controller**: `createModeController(deps)` (`match.modes`) owns the active mode and calls `input.setMode`. HUD `onStartPlacement(type)` -> `match.modes.startPlacement(type)`, `onStartRally()` -> `match.modes.startRally()`, `match.modes.cancel()` leaves a mode.
- **Minimap** (`src/client/ui/minimap/`, `mountMinimap({ container, getState, registry, playerId, renderer, input })`): fills the container (the HUD's `#minimap-slot`). The map is drawn as the same 2:1 diamond as the world, `px = ox + (x - y) k`, `py = oy + (x + y) k / 2`, fitted to the container with 2 px padding (`geometry.ts`, pure). Terrain and nodes/buildings are cached canvases; nodes and buildings are redrawn only when their (id, constructed) signature changes. The visible canvas (cache + units + diamond border) is recomposed at 5 Hz. The camera outline (`visibleWorldCorners()`, a screen-aligned rectangle clipped to the diamond) is a separate canvas redrawn only when the camera moves, so panning stays smooth. Trees are exact footprints; ore, stone and berries are squares of at least 3 px with a dark rim; buildings are footprint diamonds in the owner colour (translucent while unfinished); units are pixel-aligned 3 px squares (2 px enemy) with a dark rim. Left press or drag calls `renderer.jumpTo` with the point clamped into the map; right click calls `input.issueContextOrder` at the canvas point of that world position (an off-screen target resolves to the ground point, never to an entity).
- **Temporary code** (`ui/minimap/tempMount.ts`, `input/placement/tempDev.ts`, the `canPlace:` override in `Match`) was removed in Phase 2: the game uses the sim's `canPlace`, the minimap is mounted into `#minimap-slot` by `app/hooks.ts`, and the e2e tests drive placement and rally through the HUD.
- **E2E screenshots** are written to the git-ignored `test-results/screenshots/`; `docs/screenshots/wp10/` holds the reviewed WP10 set and `docs/screenshots/phase2/` the Phase 2 gallery. `E2E_PORT` selects the preview port (default 4173) so checkouts can run side by side.

## Phase 2 integration

Rules decided while connecting the ten work packages and running the real game end to end.

- **Wiring** (`src/client/app/hooks.ts`, passed to `App` by `boot`): `onStartPlacement` calls `match.modes.startPlacement` and `hud.setPlacing`; `onStartRally` calls `match.modes.startRally`; `onMatchReady` sets `match.onInvalid` to HUD error toasts, follows `match.onModeChange` so the HUD's `placing` clears when a mode ends (placed, Esc, right click, replaced), and mounts the minimap into `#minimap-slot` (retrying for a few frames until the HUD has rendered it). `Match` exposes `minimap`, `onInvalid` and `onModeChange`; `createModeController` takes an additive `onChange` callback. The placement ghost always asks `sim.query.canPlace`.
- **Debug hook** (additive to `GameDebugHook`, dev and e2e builds only): `inputMode()`, `ghost()`, `overlayStats()` and `minimapToPage(x, y)` replace the removed `window.__wp10`. `?paused=1` in the page URL starts every match paused (so a loaded save can be compared tick for tick).
- **Real stats in the HUD.** Card times come from `resolvedStat` with no fallback; the placement ghost colours tiles from the real per-tile result. `runtime.resolvedStats` is rebuilt in `rebuildRuntime` (new game, load) and on every tech completion; gathering, carrying, speed, construction time, production time, population and income all read it (tests: `tests/sim/economyLoop.test.ts`: Iron Axes +15% measured on the real harvest, Hand Carts carry 15 and speed x1.1, Themata farm rate x1.1, build time halved by a civ modifier).
- **Build menus** list only `buildable` buildings, so the Town Center is in none. A researched tech is not on its building's card.
- **Delete** refunds a building's queued units and techs in full, the same rule as `cancelQueue` (unfinished buildings still refund `costPaid`). The queue is cleared at once and the building is removed in cleanup.
- **Picking** (`render/picking.ts`): units first (sprite body box); then buildings and nodes whose ground footprint contains the click (a ground click next to a tree or deposit is a ground click, however tall the sprite); then the body that rises above a footprint, limited to the footprint's screen width for buildings and to a narrow column for nodes (tree 36 px wide and 64 px tall, bush 44 x 30, deposit 92 x 44), so a click about three tiles up-screen of a tree is ground. Within a tier buildings beat nodes, then front-most wins. Anything more than a tile or two of canopy above a node is not clickable by design.
- **Auto-continue and rally** go through `assignOrder`/`replace`, which start the real WP6 gather handler: the builder of a Lumber Camp, Mining Camp or Mill gathers the nearest matching node, the builder of a Farm works it (the other builder of a farm idles: a farm takes one worker, the lower unit id acts first), a unit rallied to a node or own farm gathers it.
- **Minimap** draws a tree as a crisp one-pixel mark when its footprint is under 2 px (the HUD's minimap is about 168 px wide, so a tile is about 0.7 px).
- **E2E conventions.** `tests/e2e/helpers.ts` holds the shared UI drivers: matches start on a pinned seed (see E2E determinism below), and tests still find open ground and valid building spots from the live state and the placement ghost (`validGhostSpot`) rather than fixed offsets, and keep clear of the HUD (the bottom 190 px and the top bar are panels). Commands apply on the next tick, so a test steps at least one tick after a click or a cheat before reading state. Resource cheats only shorten waiting; scenario 8 also uses `instantBuild` and `instantResearch` as plan 9.3 allows. Screenshots go to the git-ignored `test-results/screenshots/` and the reviewed gallery is copied to `docs/screenshots/phase2/`.
- **Scenario coverage** (plan 9.3): 1 and 2 `phase1.spec.ts`; 3 to 11 `phase2.spec.ts` (3 right-click a tree, 4 House, 5 villager and rally on berries, 6 population cap and release, 7 Iron Axes rate, 8 four ages with cheats, 9 Silk Workshops, 10 save, reload, load, 11 minimap click and drag, pan, zoom, clamp); `wp10.spec.ts` covers minimap pixels, overlays, placement ghost and rally mode.

## WP11: economy bot and balance

- **Bot** (`src/bot/`, uses only `src/sim` index exports and `src/data`; lint-enforced). Three steps per decision: `readView(sim, playerId)` copies the public state into a `BotView`; `decide(view, query)` is a pure function from the view and read-only queries (`availability`, `canPlace`) to `CommandInput[]`; `EconomyBot.update(sim)` stamps `playerId`/`seq` and returns the commands to pass to `sim.step`. It decides once every `PLAN.decisionIntervalTicks` (20) ticks, never between, and contains no randomness, so a run is a pure function of the seed. All tunable habits (shares by age, margins, tech order) are in `src/bot/plan.ts`; none of it is game balance.
- **Rules per decision**, in order: House when `cap + 10 * Houses in flight - population` is under 3; age advance the moment it is available and affordable (a waiting second queue item is cancelled and refunded); villagers while the queue holds fewer than 2 items, pausing when the advance is within about 70 s (Founding) or 30 s (later) of food income of being affordable; the age's two required buildings once 40% of the advance's food is banked, reserving their cost so farms and techs do not eat it (farms may still spend it while food is under 300); idle villagers go to the resource furthest below the age's share (plus stockpile feedback); gatherers whose node has drifted over 6 tiles from a drop-off are moved; one villager is rebalanced when a resource is two below its share; one economy tech per decision.
- **Sites.** Mills, Lumber Camps and Mining Camps go next to the densest free nodes nearest the Town Center whenever the best node is more than 4.5 tiles from every drop-off, planned ones included; a second villager `assist`s an unfinished camp. Farms go next to Mills and the Town Center, never over another farm. Houses and large buildings keep one free tile around them and at least 7 to 8 tiles from the Town Center. Every site is confirmed with `canPlace`. A node is only used if a flood fill over the bot's own map of buildings and nodes reaches a tile next to it (a camp can wall in a tree) and it is within 26 tiles of the Town Center.
- **Test** (`tests/sim/economyBot.test.ts`, harness `tests/sim/botHarness.ts`): five seeds to the Empire Age against the plan 5.7 thresholds; no unit with a moving order (`toNode`, `toDropOff`, `toSite`, `walking`, or a pending path) keeps its position for 30 s; resources never negative; no `CommandRejected`; node gatherer slots, held harvest slots and abandoned foundations; decisions land only on 20-tick boundaries; two runs give identical command logs and state hashes. About 30 s of CPU.
- **Balance.** No `src/data` value changed; the targets are met with the reference build order. Timings, income curves and observations are in `docs/BALANCE.md`.

## WP12: determinism, saves, performance

- **Replay** (`src/sim/replay.ts`, exported from `src/sim`): `replay(config, log, ticks, { hashEvery, saveLoadAt, data, onEvents })` rebuilds the match and feeds each `{ tick, commands }` entry to the step where `state.tick === tick`, returning the final sim, the hashes (every `hashEvery` ticks and at the end) and the final hash. `saveLoadAt` replaces the sim by `deserialize(serialize(sim))` before those ticks. `CommandRecorder` builds a log from a live run; `commandLogToJson`/`commandLogFromJson` round-trip it. The long-run tests (`tests/sim/determinism.test.ts`) record a 30,000-tick scripted game (`tests/sim/scriptGen.ts`: seeded choices of valid commands through the public sim API, all four ages, plus a few invalid commands), then check two replays, replays with saves at seeded random ticks and every 50 ticks through a busy stretch, two matches stepped alternately in one process, and a save whose object keys were reversed. No nondeterminism was found; nothing needed fixing.
- **Saves** (`src/sim/serialize.ts`): the file is canonical JSON `{ version, state }`; only `GameState` is stored (occupancy, resolved stats, the path component cache and the movement spatial hash are rebuilt by `simFromState`). `deserialize` throws `SaveError` with a `code` (`invalidJson`, `notASave`, `unsupportedVersion`, `corrupt`); `SaveVersionError` (code `unsupportedVersion`) carries `found`, `expected` and `direction` (`newer`, `older`, `unknown`). `MIGRATIONS[n]` upgrades a version-n state to n+1 (empty at version 1); an older version with no migration is refused like a newer one. A structural check turns a damaged file into `corrupt` (with a message naming the entity or queue item) instead of a half-loaded game: ascending unique entity ids; known def ids of the right kind (including unit and tech ids in production queues, at most `MAX_PRODUCTION_QUEUE` items, integer costs and tick counts with `ticksDone <= ticksTotal`); unit positions (current and previous), waypoints, move orders and rally points inside the map; building and node footprints inside the map; facing 0 to 7; order types and shapes; every entity id a rally, builder or gatherer list or path request refers to must exist (ids are never reused and cleanup clears those references when it removes an entity); an order's target need only be a positive integer, because a node depleted or a building deleted this tick leaves orders pointing at it until they next run; integer resources, costs, carried amounts and node amounts; ages 1 to 4; map array length. It is a structural check, not a rules check: whether an order still makes sense is left to the sim. A `version` that is not a whole number gives `SaveVersionError` with direction `unknown` and a message saying it is not a number (or not a whole number), not the "this game reads version 1" wording. `parseSave` in the UI maps these to its existing result kinds; a newer save adds "update the game to open it". `tests/sim/fixtures/save-v1.json` is a committed version-1 save (48x48 map, 421 ticks, queues, orders, a half-built house); `tests/sim/saves.test.ts` fails if it stops loading or re-serialising byte for byte. Regenerate it with `UPDATE_SAVE_FIXTURE=1 npx vitest run tests/sim/saves.test.ts` after bumping `SAVE_VERSION` and adding a migration.
- **Sim performance** (plan 9.4). `src/sim/stress.ts` builds the stress match (200 villagers, 150 buildings, about 1,830 nodes, everyone gathering, a tenth of the villagers re-tasked every 25 ticks by a scripted player). Changes, all behaviour-preserving (the stress hashes at ticks 1,000 to 4,000 are identical before and after): the A* inner loop is one flat loop over typed tables with the walkability checks of the four orthogonal neighbours reused by the diagonals, and the open list is a hole-based binary heap; `canonicalJson` builds one string instead of an array of pieces and no longer concatenates a path string per value. Measured on this machine (node, 2,500 ticks after 150 warm-up): average 0.44 ms -> 0.27 ms, p99 11.5 ms -> 5.4 ms, worst 16 to 40 ms -> 7 to 16 ms (run to run noise from GC and the shared CPU); the first ticks, when all 200 villagers ask for a path at once and the code is cold, take 12 to 28 ms. The structural worst tick is a saturated path queue (20,000 expansions, about 9 to 12 ms); `PATH_BUDGET_PER_TICK` was not changed. `tests/sim/performance.test.ts` asserts average < 2 ms and p99 < 12 ms with a generous max.
- **Render and HUD cost** (`scripts/perf-browser.mjs`, run by hand with `E2E_PORT=5470 node scripts/perf-browser.mjs`; not a CI test): `EntityLayer` keeps buildings and nodes in a list sorted once per change of the entity set, looks each sprite up once, reuses its `DrawnEntity` records and only sorts and merges the visible units each frame; buildings and nodes get fixed even `zIndex` layers and units the odd layer in the gap where they stand, so Pixi sorts only when a unit walks past something. A frame with 1,780 entities in the culled rectangle went from 3.9 ms to 0.36 ms of JS (and 739 entities from 1.8 ms to 0.29 ms) in a node micro-benchmark of old against new on the stress match, with identical `drawn` output over 215 frames. `HudController.refresh` returns without notifying when nothing the HUD shows changed, and unchanged parts of the view-model keep their identity so `Hud` skips re-rendering them (`useMemo` on the elements). Frame-cost counters live in `debug/perf.ts` (off unless `__game.perf.enable(true)`).
- **Debug hook additions** (additive to `GameDebugHook`, dev and e2e builds only): `startStress(seed?)`, `setZoom(zoom)` and `perf.enable/reset/snapshot`. `Match.beforeTick` lets the stress match's scripted player issue commands each tick. `performance.mark/measure` entries `rts.mapgen` and `rts.art` record map and art generation time.
## WP13: UX pass and debug tools

Rule changes (sim):

- **Last Town Center.** `delete` is rejected whole with `cannotPerform` if it would leave the player with no completed Town Center (a second Town Center, or an unfinished foundation, can still be deleted). The HUD maps `cannotPerform` on a `delete` to "Your last Town Center cannot be demolished".
- **Population counter.** `popUsed` is living units only; queued units no longer count. The hold test is unchanged (`popUsed + popCost > popCap`). The bot keeps planning against living plus queued units (`src/bot/view.ts` adds the queue back); its pacing is unchanged (seeds 1 to 5: Township 6:16 to 6:24, Citadel 12:34 to 13:35, Empire 18:23 to 19:55).
- **Spawn spreading.** `findSpawnTile` skips tiles that hold an idle unit and searches up to 6 rings out (falling back to any free tile so production never stalls). Idle separation (`SEPARATION_RADIUS` 0.3) only pushes units apart to 0.3 tiles, which is why stacked spawns looked like one unit: units that share a tile are never visually distinct, so the fix is to spawn them on different tiles.
- **Rally onto a full or depleted node.** At spawn, a full gather target is replaced by the nearest free node of the same resource within `RALLY_RETARGET_RADIUS` (16) tiles of the rally target; none: move to the rally point and `VillagerIdle` is emitted once. When a rally node is removed as depleted, cleanup moves the rally to the nearest surviving node of the same resource within 16 tiles, else the rally becomes a ground rally at the old spot.

Client:

- **Delete confirmation.** Deleting a selection that holds a completed own building needs a second Delete within 2 s (`DEMOLISH_CONFIRM_MS`) on the same selection; the first press toasts "Press Delete again to demolish". Units and unfinished buildings go at once. The command-card Delete action uses the same path.
- **Toasts merge.** An identical live toast (same kind and message) is merged into the existing one: its count rises ("Spearman trained ×3") and its 4 s lifetime restarts, timed by the match clock. "Unit trained" toasts are routine: together they may hold at most half the 4 slots (the oldest routine toast makes room), they never push out anything else, and with every slot taken by non-routine toasts a routine one is dropped. When the slots are full, the next to go is a routine toast, then a non-error, then the oldest. Errors are therefore never crowded out by steady production; age advances are banners, a separate channel.
- **Progress bars** sit just above the highest visible pixel of the building's art (measured once per texture from the canvas it was drawn from; the footprint estimate `14 * size + 12` / `28 * size + 24` is the fallback when it cannot be read). The offset is in world pixels, so the bar stays on the building at 0.5x, 1x and 2x; its own size (36 x 5 px) and the gap above the art stay constant on screen.
- **Pause key.** F10 and Pause go through the HUD, which ignores them while the in-match menu holds the game paused.
- **Stable card slots.** A building's items take slots from its data order (units, then techs) for the civ; civ-hidden items (Lancer for Byzantines) take none, items not yet available stay greyed in their slot, a researched tech leaves its slot empty (`commandCard.ts`).
- **Selection facts.** `SingleSelectionVM.facts` (additive): passive income, drop-off icons, population provided, gatherer count for nodes and farms.
- **Costs and button layout.** A command-card button is 60 x 48 px in two bands: the item icon on top (24 px; 36 px and centred when the item is free) and, below it, a 22 px cost band of up to two rows of two costs (resource icon plus amount, 9 px type, `1k` style above 999). The hotkey letter is in the top-left corner beside the icon. Icon, hotkey and costs never overlap and nothing is clipped at 800x600, 1280x720 or 1920x1080 (`tests/e2e/commandCard.spec.ts` measures the bounding boxes on the age buttons, also padded to four costs). An unaffordable amount differs by text colour only.
- **Several cancels in one tick.** The sim applies a tick's `cancelQueue` commands in `(playerId, seq)` order and each `index` is read against the queue as it is when that command applies (unchanged, so existing command logs replay identically). A client that sends more than one cancel for the same building in one tick must therefore lower each later index by the number of earlier cancels in that batch that sat in front of it. `HudController.cancelQueueItem` does this: pending cancels are tracked by the index the player clicked (the queue shows them), the command carries the adjusted index, so exactly the clicked items are cancelled and refunded, head included, in any click order. The command shape did not change.
- **Cancel while paused.** A queue cancel is shown as pending (dashed, "Cancelling") until a tick applies it; while paused a toast says it applies on resume. A second click on a pending item does nothing.
- **Layout.** The top bar tightens below 1180 px and wraps onto two rows below 1024 px (`--topbar-h`); the bottom panels touch (no strip of world) and the minimap panel is about 2:1 so the diamond fills it. Mounted-unit icons (Horseman, Lancer, Cataphract) are drawn side-on (`iconFacing`).
- **Debug overlay (F3, dev and e2e builds only; the chunk is not in the production bundle).** `src/client/debug/`: frame rate, tick time (avg/max over 120 samples), entity counts by kind and type, path queue; toggles for occupancy grid, unit paths, approach tiles of the selection (and of selected units' targets) and the tile under the cursor; cheats (add resources, instant build, instant research and training, spawn any unit by arming a click, state hash) issued as `cheat` commands. Profiling and drawing are attached only while the overlay is open (`Match.profiler` / `Match.debugFrame` stay null otherwise).
- **Test timeouts.** `vite.config.ts` sets `testTimeout` 180 s; the heaviest determinism tests carry explicit timeouts.
- **Screenshots.** `docs/screenshots/` holds one curated set (12 images); e2e writes only to the git-ignored `test-results/`.
- **Production queue layout.** The queue row in the selection panel never wraps: up to `MAX_PRODUCTION_QUEUE` (10) items share the panel width (40 px each while there is room, shrinking evenly). At 800x600 a 6-item queue used to wrap below the visible area.
- **Debug FPS.** The F3 panel shows one decimal below 10 fps (a slow software-GL frame rate no longer reads "0 fps").

E2E determinism (dev and e2e builds only):

- **Pinned map.** `?seed=N` in the page URL fixes the map seed of the next New Game (`app/seed.ts`; production builds ignore it). `tests/e2e/helpers.ts` `startMatch` always pins one (`DEFAULT_SEED` 1) and starts paused (`?paused=1`), so no tick runs before the test takes over. `seeds.spec.ts` deliberately plays match start, gathering and House placement on six other seeds.
- **Client clock.** Double click (400 ms), double tap of a control group (400 ms), the demolish confirmation (2 s), toast and banner lifetimes and order markers (750 ms) are timed by `Match.clock` (`app/clock.ts`), `performance.now()` by default. `__game.freezeClock()` stops it following real time and `__game.advanceClock(ms)` moves it; `startMatch` freezes it, so these windows depend on what the test does, not on machine speed. Helpers that must not be the second half of a double (`clickUnit`, `clickBuilding`, `recallVillagers`, `selectAllVillagers`) advance it by `SEPARATE_MS` first.
- **No timer waits.** `__game.step(n)` also rebuilds the HUD (`HudController.sync`) and redraws the minimap at once instead of waiting for their 10 Hz and 5 Hz timers; `step(n, false)` skips that (`stepUntil` uses it for long runs). `__game.pickAt(x, y)` returns the entity a click at a page point would pick, so a test can verify a click target (`pickableTree`) instead of assuming open ground. Tests use no `waitForTimeout`.
- **Parallel suites.** `E2E_PORT=N` also selects `dist-e2e-N/` and `test-results-N/`, so two suites can run side by side. `retries` is 0.

## Rendered art (voxel renderer and pre-rendered sheets)

The default art in dev and production builds is ray-traced at load from voxel models (`src/client/art/rendered/`), a port of the approved art-direction mockup: midday sun (azimuth 150°, elevation 50°) with sky and bounce light, ambient occlusion, soft shadows, procedural weathered materials at full grit (dirt rising from the ground, rain streaks, moss on roofs, cracks), reduced to one shared 256-colour palette with serpentine Floyd-Steinberg dither. The procedural canvas art stays as the fast alternative.

- **Two sources.** Units (every one, 8 facings, all animations), trees and berry bushes come from sprite sheets pre-rendered offline in Blender (`scripts/art/`, see "Pre-rendered sheets" below); buildings, gold and stone deposits and the terrain are ray-traced at load by the voxel renderer. Both read the same light and tone-map constants (`rendered/artConstants.json`) and share one palette, so they sit in one world. The voxel units and trees remain as the fallback when a sheet is missing or fails to load (they are then rendered at load as before).
- **Switch.** `?art=rendered` / `?art=fast` (`art/select.ts`); `?sheets=0` turns the sheets off (voxel units and trees). Default: `rendered`, except the e2e build, which defaults to `fast` so the browser suite keeps its speed; `tests/e2e/renderedArt.spec.ts` runs the rendered art explicitly. `?artWorkers=0` forces main-thread rendering and `?artCache=0` bypasses the cache (both for testing). The rendered manifest is composed with the procedural one (`art/composite.ts`): each sprite id goes to the first provider that claims it (sheets, then voxel renderer); unclaimed ids and the "?" fallback come from the procedural art. The sheets load first and the voxel renderer skips the jobs of ids they cover (`covered`).
- **Pipeline.** Model builders (`models/`) fill a voxel grid (24 cells per tile for buildings, 30-46 for units, 28-48 for nature) with boxes, roofs, arches, domes, capsules and discs; `finalize` blurs the occupancy into the fields used for smooth normals and AO. `render.ts` casts one view ray per subsample (2x2 supersampling) in the game's exact projection (`project.ts`, `screenY = (x+y)*16 - z*32*sqrt(1.5)`; on the ground it is `iso.ts`), one jittered shadow ray towards the sun, blurs shadows depth-aware, shades with `materials.ts` and tone-maps (`light.ts`). A pixel is model when at least half its subsamples hit (fully opaque, never a fringe); otherwise it holds the ground's shadow and contact occlusion as black with alpha (the same premultiplied or not). Units then get an unsharp mask, a darker inner silhouette edge and a soft black outline. Pixels are dithered to the palette.
- **Palette.** `rendered/palette.json` (read by `paletteData.ts` and by the sheet pipeline) holds 240 colours fitted by median cut to the voxel buildings and deposits, the terrain (weighted up) and the colours of the sheets (`scripts/art/sheet-histogram.json`, written when sheets are packed): `npm run art:palette`, i.e. `node scripts/art-tool.mjs palette`; re-run after big material or light changes, then `npm run art:sheets` to re-quantise the sheets to it. The other 16 entries are a player-colour ramp: team cloth (`M.BLUE`, `M.BLUEPAINT`) is stored as a shade level per pixel and each atlas page is tinted to a player's ramp the first time that colour is drawn (`teamSprite`). Player colour is the player's `color` (Byzantine purple by default). Sheets work the same way: team surfaces are 16 reserved palette indices (one per ramp level) whose colours are swapped for `teamRamp(color)` when a sheet's textures are made for that colour (`sheet/meta.ts layerPixels`), so one sheet serves any player colour.
- **What is rendered.** Buildings: every building in an early look (timber, wattle and daub, thatch or shingle, rough footing; ages I-II) and a late look (dressed stone with brick bands, arches, tiled roofs; ages III-IV); the Town Center has one look per age (dome only from age III); buildings that only exist later have only the looks of their ages. `models/looks.ts` maps (building, age) to a look; the renderer passes the owner's age (`SpriteContext.age`) so the shown look follows the player's age. Each look has the three construction stages (`foundation`: footings in a dug trench, stakes and line, a pile of timber or stone; `scaffold`: walls laid unevenly to about half height, hollow, with timber scaffolding and a ladder; `complete`). Voxel units (the fallback when sheets are off or missing): 8 rendered facings (no mirroring, so the baked shadows stay consistent), 4 states (`idle` one frame; `walk`, `work`, `carry` two frames; only villagers have their own carry pose, the others reuse walk), posed with a joint rig (hips, knees, shoulders, elbows, held tool). Nodes: 8 voxel tree variants (fallback; oak, cypress, olive, stone pine) picked by a hash of the entity id (`SpriteContext.seed`; nodes with variants are not mirrored), 2 berry bushes, 2 gold and 2 stone deposits. HUD icons of units are a larger render; building and node icons reuse the sprites; tech, resource, age and civ icons keep their glyphs.
- **Frames.** All looks and stages of a building id share one frame and anchor (`buildingFrame`); units keep the procedural art's frame sizes and anchors, so picking boxes behave the same. Sprites are trimmed into atlases (`atlas.ts`, 2048 px pages, 2 px gutter, Pixi textures with `trim`/`orig`; magnification is nearest so zooming in stays crisp). `SpriteAnimation.modelTop` gives the first row of model pixels (not shadow): progress bars and building hit boxes use it instead of scanning the texture.
- **Loading.** `load()` renders the jobs the Founding Age needs (age-I looks, villager, spearman, nodes, terrain) on a pool of module Web Workers (`navigator.hardwareConcurrency` capped at 4) with progress, then resolves; the rest renders in the background and is merged when done (until then a later look falls back to the earliest one and unrendered units to the procedural art). Without workers (unsupported, blocked, or not starting within 15 s) the jobs run on the main thread in ~12 ms slices. The finished atlases are stored in IndexedDB under a key made of a build-time hash of the art sources (`__ART_HASH__`, `vite.config.ts`), the palette and the job list; a later load reads them back and skips rendering. Every storage call is wrapped, so a missing or blocked IndexedDB is just a cache miss.
- **Terrain.** Four seamless textures (grass, a second grass, dry grass, worn earth) that repeat every 8 tiles in x and y, which makes each a 512x256 screen-space tile. `TerrainLayer` fills a chunk by copying, per pixel, one texture's pixel chosen by low-frequency world noise (grass variants, dry patches) and by worn-earth aprons around buildings, farms and deposits, with per-pixel jitter for ragged dithered borders (so the terrain stays in the palette and shows no seams). Aprons are recomputed when the entity set changes and only chunks whose aprons changed are re-baked.
- **Pre-rendered sheets.** `src/client/art/sheets/<unit>.json` + `<unit>-N.png` (and `tree`, `berryBush`), committed, made by `npm run art:units` / `npm run art:trees` (Blender via `scripts/art/run.mjs`; setup and times in `scripts/art/README.md`; never in CI or at runtime). Cycles renders in the exact projection (3x supersampled, denoised); post-processing ports the voxel renderer's tone map, 1-bit coverage alpha (50 %), unsharp mask, dark inner edge and soft outline, and the shadow-strength formula; figures are dithered to the shared palette. PNGs are indexed: 0 transparent, 12 ground-shadow levels, 7 outline levels, 16 team levels, then the shared colours used. `sheet/png.ts` decodes the indices itself (no colour management); `sheet/manifest.ts` serves the sprites: per state and facing a `SpriteAnimation` with trimmed textures (`trim`/`orig` in the untrimmed frame, so all frames share one anchor), the ground shadow as a separate texture (`shadows`, drawn by the entity layer on a container under all entities, so shadows never cover figures), the figure box per frame (`bodies`, unit hit boxes; shadows are never clickable) and `modelTop` (bars). States: `idle` (2 frames), `walk` (8), `attack` (8: wind-up, strike or release, recover), `death` (7, plays once, `loop: false`), `corpse` (the last death frame darkened and desaturated); villagers also `chop`, `mine`, `farm`, `forage`, `build` and `carryWood`/`carryFood`/`carryGold`/`carryStone` (8 each). The renderer picks the villager's job and load from its order and carried resource (`unitAnimDetail`) and draws a working unit facing the node or building it works on (`facingToward`, drawing only); art without a specific state gets the next one along the one fallback chain, `UNIT_STATE_FALLBACK` (`chop`... to `work`, `carryWood`... to `carry`, `work` and `walk` to `idle`, `carry` to `walk`, `attack` and `death` to `idle`, `corpse` to `death`), applied by the renderer and the overlays with `resolveUnitState` (merge with M2: the sheet manifest's own alias table and the separate `GENERIC_STATE` map were folded into it). Walk and carry animations carry `cycle`, the ground distance (tiles) one loop covers from the rig's stride, and their frames advance with the distance the unit actually moved, so feet do not slide at any speed or game speed. Combat drives attack (synchronised with the release), death and corpse (WP27, below); `__art.preview(id, state)` still forces a state for art reviews. Units are about 23 px tall (cavalry and siege to scale), HUD unit portraits are a larger render in the sheet (`icon`). Trees: oak x2, cypress, olive, stone pine x2 (space-colonisation branches, leaf cards), berry bushes x2, picked per entity id as before. The game shows no stumps or picked-clean bushes (depleted nodes disappear), so none are rendered.
- **Debug.** `window.__art` (dev and e2e builds): `mode()`, `report()` (load timings, worker count, completeness), `sheets()` (sheet load time, bytes, sheets loaded and failed), `sheetStates(name)`, `preview(entityId, state)` (force an animation state), `colour(entityId, color)` (draw one entity in another player colour), `recolourDiff(...)` (compare a frame in two colours), `audit()` (every sprite id's textures over all states, facings, ages and variants, with sizes and opaque pixel counts), `drawnTexture(id)` (label of the texture an entity was drawn with) and `issue(command)` (staging). `node scripts/art-tool.mjs sheet|time` renders jobs in Node for contact sheets and timings; `node scripts/art-shots.mjs` stages scenes in the e2e build for screenshots.

## WP24 (repair, movement, two-player map)

Rules as implemented for PLAN-M2 4.7, 4.11, 4.12, 4.15 and `directPath`; details the plan left open are listed here.

- **Repair order** (`orders/repair.ts`). `begin` returns null if the building is gone or unfinished; a full-hp building is handled in `run` (done, with `VillagerIdle` if nothing is queued, so the player is told). The unit walks like `assist` (`followPath` to the footprint), and in `repairing` it is in `repairerIds` (ascending). Leaving adjacency returns it to `toSite` and removes it from the list. A path used up short of the building ends the order. `end` removes the unit from the list.
- **Repair command.** After `validateOwnUnits`: `unknownEntity` (no such entity), then `invalidTarget` for a non-building, a foreign building, an unfinished one, one with hp 0 or one at full hp, then `cannotPerform` if any unit's `builds` lacks the type. An empty unit list is a no-op like the other commands.
- **Repair progress** (`runRepair`, after construction in `runConstruction`). Buildings are processed in ascending id; `repairerIds` is pruned to units in `repairing` on that building. `buildTime` is the resolved build time (`buildTicks / TICK_RATE`). Both accumulators are snapped to a 1e-9 grid. A tick is atomic: if the whole hp bought this tick is not affordable, neither accumulator changes (so `repairAccumulator` stays in [0, 1) while stalled). Cost accumulation uses the resolved cost of the def (`resolvedCost`). Reaching max hp, or any completed building found at max hp, resets both accumulators. The total over a full repair is `floor`-bounded to 50% of cost (the unpaid fraction is under 1 per resource).
- **Construction HP** (`updateConstructionHp`) is unchanged from Phase 0 and now has tests: 10% at placement (min 1), linear in progress, damage persists, completion sets `builtHp = maxHp` without healing.
- **Separation** (`movement.ts`). The idle pass now includes stationary attackers (`isStationaryAttacker`): no path, no pending request, and order `attack` in `attacking`, `attackMove` in `engaging`, or `hold` with a target. A pair uses `COMBAT_SEPARATION_RADIUS` (0.45) if either unit is an attacker, else `SEPARATION_RADIUS` (0.3), so M1 idle behaviour is unchanged. Pushes onto blocked tiles are skipped as before.
- **`directPath`** sets `path = { waypoints: [target], nextIndex: 0, occupancyVersion }` when `segmentWalkable` holds from the unit to the point, drops a queued request for the unit and clears `pendingPathRequestId`; otherwise it changes nothing. Non-finite coordinates return false.
- **Two-player map** (`mapgen.ts`, only when `players.length === 2`). Player 1's start is drawn exactly as in M1 (the same three rng draws), player 2's Town Center footprint `(tx, ty, s)` becomes `(W - tx - s, H - ty - s)` and its starting units are player 1's at `(W - x, H - y)` with facing + 4. Only player 1's guaranteed clusters are placed (not restricted to the half: with the M1 mirror flag the start sits on the diagonal); their mirror is reserved in the tag grid, so scatter and forest keep clear of it. Scatter and forest tiles must satisfy `tx + ty + 2 * (size - 1) <= (W + H) / 2 - 3`; scatter counts are `ceil(count / 2)`. After all placement, every node is mirrored (created after all originals, so player 1's nodes have the lower ids) and player 2's `guaranteed` report is the mirrored player 1 report. Validation is unchanged: it already requires every Town Center perimeter (and the units and guaranteed nodes) to be reachable from the first one. One-player and 3+ player maps take the M1 path with no rng changes; `tests/sim/fixtures/mapgen-m1-hashes.json` holds state hashes recorded from the M1 generator for 20 seeds at sizes 120 and 64 and `tests/sim/mapSymmetry.test.ts` compares against them.
### WP22: projectiles and defence

- **Impact (4.4).** Step 9 walks `state.projectiles` in ascending id. While the target entity exists (unit or building, hp 0 included) `to` follows its anchor; `ticksLeft -= 1`; at 0 the projectile is removed. The primary target takes `damage` only if it still exists with hp > 0 and is an enemy of the projectile's owner; a shot at a target already at 0 hp is wasted (no `lastAttackerId`, no alert). Credit goes to `sourceId`/`owner` whether or not the shooter lives.
- **Splash** (fire from a unit def whose resolved profile has `splash`): all living enemy units (centre within radius of `to`) and buildings (footprint distance within radius, foundations included) except the primary, each for `max(1, floor(computeDamage(source profile at impact, victim) * percent / 100))`. The queries run with an unlimited budget and the victims are applied in ascending id, so neither the grid visiting order nor creation order changes the result. Splash happens even if the primary is gone.
- **Helpers** exported from `systems/projectiles.ts` (not contract): `projectileFlightTicks(ctx, kind, dist)` and `anchorOf(ctx, target)`; WP21 may use them for unit shots.
- **Town Center volleys (4.10).** `runBuildingAttacks` visits completed buildings with `attack !== null` whatever their hp. Reach is measured from the footprint centre to the unit centre (`reach = range + 0.75`). `cooldown` decrements first; a held `targetId` is kept while it is a living enemy unit in reach. With no valid target, `tick >= nextScanTick` and budget left, one scan runs (units only, radius `reach + SPATIAL_QUERY_PAD`, at most `ACQUIRE_MAX_CHECKS_PER_SCAN` checks charged to `runtime.acquireBudget`), choosing the lowest (tier, d squared, id) with tier 1 = `autoAcquire` and `targets: 'any'`, tier 2 = other units; then `nextScanTick = tick + 10`. A scan that finds nothing therefore waits up to 10 ticks. Superseded in Phase 2 integration (below): the scan runs in step 4; step 8b only re-checks and fires. The volley is `arrows` projectiles from the footprint centre with damage computed at fire time (`attack` vs the target's armour, no bonus) and `flightTicks` from the centre-to-unit distance; then `cooldown = cooldownTicks` (40), so the period is exactly 40 ticks.
## WP23 (death and outcome)

- **Death (step 11, `runDeath`)**: every unit and building with `hp <= 0` that is not already in `pendingRemoval` emits `UnitDied` / `BuildingDestroyed` (buildings carry `size` and `constructed`), updates stats and joins `pendingRemoval`; the existing cleanup in the same tick removes it. Entities flagged by a `delete` command in the same tick are skipped: a deletion is neither a loss nor a kill. Carried resources vanish with the unit. A destroyed building's queue is emptied with no refund, and a destroyed foundation's `costPaid` is lost (`delete` still refunds both).
- **Kill credit**: owner of `lastAttackerId` while that entity still exists (it still does when shooter and victim die on the same tick); else the owner of the lowest-id projectile still in `state.projectiles` whose `sourceId` is that attacker; else `null`. Never the victim's own owner or the neutral player. `unitsKilled` / `buildingsDestroyed` count only credited kills; `unitsLost` / `buildingsLost` count every death, including the destruction of a defeated player's entities.
- **Recovery**: no new code in cleanup. Gatherers whose drop-off died re-choose a drop-off, builders of a destroyed foundation go idle, `gathererIds`/`builderIds` slots are released, rally targets are cleared (tests in `tests/sim/deathOutcome.test.ts`).
- **Population**: `popCap` drops with destroyed Houses; if `popUsed > popCap` nobody dies and production holds (the M1 production rule).
- **Defeat (step 12, `runOutcome`)**: conquest mode only. A `playing` player is defeated when no completed building with non-empty `trains` and no living (`hp > 0`) unit whose def `builds` the `start.centerBuilding` remains. Defeat sets `outcome`, `defeatedTick = tick + 1` and emits `PlayerDefeated{conquered}`. The destruction of defeated players' entities (`hp = 0`, `lastAttackerId = null`, so no kill credit) runs every tick for every `defeated` player in every mode, so it also covers the `defeat` cheat and `resign`; the entities die in step 11 of the next tick.
- **Victory**: when exactly one real player is `playing` (and the match has at least two real players, and `endedTick` is null) that player becomes `won`, `match.winner` and `endedTick = tick + 1` are set and `MatchEnded` is emitted; `runObjectives` completes `conquest:<id>` for a `won` player in the same tick. No player `playing`: `MatchEnded{winner: null}` (draw), no objective completes. Sandbox and one-player matches never end.
- **Resign**: accepted while `playing` in any mode; a `defeated` or `won` player is rejected with `playerDefeated`.
## WP21: combat core

Implements PLAN-M2 2.3 (spatial index), 4.2, 4.3, 4.5, 4.6 and the WP21 commands of 4.8 in `src/sim/systems/combat/` (`spatial.ts`, `acquire.ts`, `engage.ts`, `attack.ts`, `stance.ts`) and `systems/orders/attack.ts`, `attackMove.ts`, `hold.ts`. Rule details decided here:

- **Spatial index.** A unit is filed under the cell of its position at rebuild (clamped); a building under every cell its footprint `[tx, tx+size)` overlaps. Queries skip cells whose rectangle is farther than `r` from the query point (no checks spent), and a building listed in several visited cells is looked at and charged once per query. The distance test uses current positions, so callers after movement pad `r` by `SPATIAL_QUERY_PAD` and re-check exactly.
- **Budget.** "Exhausted" means fewer than `ACQUIRE_MAX_CHECKS_PER_SCAN` checks left in `runtime.acquireBudget`: such a due unit keeps its `nextScanTick` and scans next tick. Every scan that runs therefore has its full per-scan budget, so with at most 128 candidates in range its result does not depend on ids. Building scans (Town Center, step 8b, WP22) share the same budget.
- **Scanning situations** (living units only): idle with `autoAcquire` (aggressive: `sight`; stand ground: reach only); an `attack{auto}` or attack-move engagement whose target is out of reach (retarget scan, reach only, candidates of tier at most the current target's); attack-move while walking (`sight`); `hold` without a target in reach, for `autoAcquire` units (reach only; villagers on hold just stand). Commanded attacks, moves and economic orders never scan. A scan when the current target is in reach is skipped entirely (no checks), but still reschedules.
- **Tiers.** Tier 0 is the last attacker when it is a valid target and, for an idle aggressive unit damaged within the last `RETALIATE_WINDOW_TICKS` (20) ticks, within `max(sight, retaliateRadius)`; otherwise within the scan radius (or in reach for reach-only scans). Retaliation beyond sight answers a recent hit, not an old `lastAttackerId`. Buildings (tier 3) are looked up only when no unit qualifies.
- **Auto engagements.** An idle unit that acquires gets `attack{auto:true}` directly as its current order, anchored at its position (the leash centre). Stand-ground auto engagements end (`done`, scan next tick) when the target leaves reach. A broken leash replaces the order by `move` back to the anchor (which ignores enemies until it arrives). Attack-move switches to `engaging` with its own anchor and returns to `walking` (fresh path, scan next tick) when the target is gone or the leash breaks.
- **Validity.** A target is valid while it exists, is a unit or building of an enemy (`isEnemy`), has hp > 0, and (siege) is a building. An `attack` command on an entity with hp 0 is rejected `invalidTarget`; a queued attack whose target became invalid is skipped when it begins.
- **Chasing.** In reach the unit stands (path and pending request cleared). Every A* request of a chase obeys `repathTick` (at most one per `CHASE_REPATH_TICKS`): a point path is re-requested when the path is gone or used up, or the target is more than `CHASE_REPATH_DISTANCE` from its last waypoint. Building targets use a footprint path; a used-up footprint path that left the unit out of reach is re-requested under the same throttle. `directPath` is tried each tick for unit targets within `CHASE_DIRECT_DISTANCE` (WP24 implements it; the stub returns false and the A* route is used). A unit inside its `minRange` walks to a point `minRange + 0.5` from the target's nearest point, away from it (trebuchet). Chasing units winding up do not request paths or move.
- **Swings.** The swing of 4.3 step 3 starts only for an `attack` in phase `attacking`, an attack-move in `engaging` or a `hold` with a target, with the target valid and in reach at step 8. A unit at hp 0 still completes a release (it acts whatever its hp) but starts no new swing. After a release `swingTargetId` is cleared. Facing is towards the target's anchor (footprint centre for buildings). A ranged release fires from the unit's position at the target's anchor; `damage` is computed at fire time with the same formula as melee.
- **Not here.** "A unit does not move while `windup > 0`" holds for WP21's own orders; for other orders given mid-swing (e.g. `move`) it needs the movement step (WP24/orchestrator) to skip units with `combat.windup > 0`.

## WP26: computer opponent (AI)

PLAN-M2 6 as built, in `src/bot/ai/` (plus the economy bot's new `plan`/`reserve` parameters). The AI is a command source only: it reads `sim.state` and `sim.query`, returns stamped commands, never writes state, never touches `state.rng`, and has no resource or vision bonus at any difficulty (there is no fog of war, so it sees what the human sees).

- **Files.** `aiPlayer.ts` (cadence, stamping, save/restore), `difficulty.ts` (the 6.3 table, the 5.3 counter matrix as numbers, unit classes), `memory.ts` (`AiMemory`, strict parser), `context.ts` (one decision's working state: stockpile left, claimed villagers, sites, rally point, operation counter), `world.ts` (one pass over the entities into plain views; bucket grid with 8-tile cells; single-link clustering), `economy.ts`, `military.ts`, `army.ts`, `defence.ts`, `upkeep.ts`, `power.ts`.
- **API.** `AiPlayer.create(playerId, difficulty, seed, options?)`, `AiPlayer.restore(save, options?)` (throws `SaveError('corrupt')` on bad memory, kind, difficulty or player), `update(sim)`, `save()`. Extras (not contract): `memory`, `firstWaveTick`, `isDecisionTick(tick)`, `cost` (operation counts, not saved). `options.orders = 'move'` makes every combat command a plain `move` and disables repair (used to measure wave timing before combat existed; default `'combat'`).
- **Cadence.** Decides when `(tick + playerId * 7) % interval === 0` (easy 60, standard 20, hard 10); returns `[]` otherwise, and always once the player is not `playing` or the match has ended. The economy layer runs on at most one decision per game second (`decisions % ceil(20 / interval) === 0`), so easy re-plans its economy every 3 s.
- **Memory** (plain JSON, ids in sorted arrays, no Map/Set outlives a decision): `version`, `rng` (own sfc32 stream, `createRng((seed ^ (playerId * 0x9e3779b9)) >>> 0)`), `seq`, `decisions`, `phase`, `waveNumber`, `nextWaveEarliestTick`, `nextWaveForcedTick`, `wave` (unit ids, target, order point, launch tick, start power, retreat tick, raid flag), `defence` (active, centroid, since/last-seen ticks, defender ids, held villager ids, recalled), `desiredBuildings`, `firstWaveTick`, `allInTick`, the army `bank` with remainders and the last `resourcesGathered`, units ordered per upgrade line, home point. The only rng draw is the first wave's jitter.
- **Decision order.** Desired-building bookkeeping; lost Town Center; defence; repair; rebuild; unstaffed foundations; villagers first (hard); Houses for the army; military buildings; economy; army production; upgrades; rally points; waves. Later layers see what earlier ones committed (stockpile, claimed villagers, sites registered into the view so the economy's own placement avoids them).
- **Economy** (6.4). `decide(view, query, data, plan, reserve)`: the plan is the difficulty's variant of `PLAN` (`villagerTarget` 28/50/70; easy `maxAge` 3, Town Center queue depth 1, no pre-advance hold, Founding shares food 60 / wood 40; standard hold 50 s; hard caps villagers at 14 in the Founding Age (the only way to its 5:00-6:00 Township; 15 already lands at 5:57-6:08) and uses Township shares food 55 / wood 28 / gold 17, Citadel food 47 / wood 28 / gold 20 / stone 5). `BotPlan` gains optional `villagerCapByAge` and `maxAge`; with the defaults `decide` is the M1 bot exactly. Once no gold node is left within the plan's work radius (26) of the Town Center, the AI hands `decide` a work radius of 60 (all difficulties): the home deposits hold 3,200 gold on most seeds, and without the far deposits the late game ran out of gold and stalled (no Rams, Cataphracts or archers; Standard vs Standard and Hard vs Hard ended without a winner).
- **Hard's economy** (Phase 3 rework; the 14-villager design starved Hard's economy and its waves). *Villagers first:* from the Township Age the first Town Center always has a villager in production, paid before any military spending from the stockpile minus the army bank (the economy layer adds the second). *Boom, then age* (`ageUpVillagers` 36 in Township, 58 in Citadel): with that many villagers and the next advance allowed except for its cost, villager production pauses, the bank stops banking the advance's resources (and is cut to what exceeds them) and the military budget leaves the advance's cost alone, until the advance is clicked (Citadel at 16:35-22:28 against Standard, instead of 24-30 min). *Spend it all:* the military budget is the bank plus the stock above 150 (not 400), the bank share is 30%, and while a threat is answered the military may spend the whole stockpile. *Never float* (`floatProducers`): when every Barracks and Stable is busy and food plus wood beyond the bank reach 700, another Barracks (or a Stable when food is at least twice the wood) is added, up to 10 military producers (the late game is bound by production buildings, not income).
- **Army bank** (6.3 "share of income", 6.4 reserve). Each decision credits `floor(share * income since the last decision)` (income = the player's `stats.resourcesGathered`; remainders kept in hundredths) to a per-resource bank capped at 250 and at the stockpile; the economy gets `reserve = bank + whatever this decision already committed` and cannot spend it. The bank credits once the first Barracks stands **and** the player is in the Township Age or has clicked the advance (deviation: in the Founding Age food is the bottleneck; banking it pushed every difficulty's Township 2 to 4 minutes late). The military spends the bank plus any surplus above 400 per resource (hard: share 30%, surplus above 150; see Hard's economy). Military buildings and army Houses are paid from the whole stockpile; from the Township Age, an unaffordable military building is saved for (its cost is withheld from the economy that decision).
- **Military buildings.** First Barracks at 16 villagers or 6:30 (easy), 14 (standard), 10 (hard); then, once in Age 2, an Archery Range (easy, standard) and a Stable (standard); hard: a Stable in Age 2, an Archery Range from 28 villagers, then in Age 3 a second Barracks (40 villagers), Stable (50) and Archery Range (60), plus the never-float producers; a Siege Workshop in Age 3 when the difficulty uses siege. One unfinished military site at a time; sites by the base search (8 to 22 tiles from the Town Center, leaning towards the rally point). The economy layer's age buildings (Archery Range, Stable; Siege and Silk Workshops) are unchanged.
- **Houses for the army.** Once a military producer stands, a House is placed when `cap + 10 * houses in flight - population (incl. queued) < plan.houseMargin + 2 * producers` (at most 2 in flight).
- **Unit choice.** For each completed producer with a queue under 2, among the affordable, available units: highest `(1 - c) * fixed[class] + c * counter[class] - share[class]` (`c` 0 / 0.5 / 1; counter normalised by enemy fighting power; with no enemy army, counter = fixed). Hard's fixed table (used while the enemy has no army) is horse 0.35, archer 0.3, sword 0.2, spear 0.15. When a Cataphract is unaffordable (no gold), the Stable trains a Horseman. The Siege Workshop trains by rule: rams up to 2 from Age 3 (standard, hard), trebuchet 1 and Siphonarioi 3 from Age 4 (hard). Rally: every military producer rallies to the point 10 tiles from the Town Center towards the enemy Town Center (on a free tile).
- **Upgrades.** Hard: everything at its building from Age 2, one per decision, when affordable from the military budget and the building's queue has at most one item. Standard: from Age 3, the level-I techs of its two most-ordered lines. Easy: none.
- **Waves** (6.5). First wave earliest = table time + rng jitter; forced = earliest + table delay. Massing launches when `tick >= earliest` and non-siege units at least the threshold, or when the forced tick falls inside this decision interval with at least `max(3, ceil(threshold / 2))` (deviation: "inside the interval" so a forced launch never lands up to one interval after the forced tick). No launch while defending. Waves: easy 4, 6, 8, +1 up to 10; standard 10, 14, +4 up to 30; hard 4 (the raid), 12, 16, +6 up to 36 (deviation: the table's "continuous reinforcement" streamed hard's units one by one into the enemy base and lost every Hard vs Standard match; the mechanism stays in `army.ts`, `reinforceFromWave`, joining in groups of at least 4, and is used by the all-in). A wave ends when its last unit dies (next earliest = now + interval). Once a Siege Workshop stands, a wave also waits for its rams (`siege.rams`), at most 90 s past the forced tick, unless it already has twice its threshold. Above easy, after the first wave, an enemy whose fighting power is under a quarter of the massed army's is attacked at once (3+ units), and fresh units reinforce the active wave (groups of 4) while that holds: AI-vs-AI games must end. Attacking (adapted to the WP25 balance: production buildings and the Town Center are armoured against blows, so only breachers raze them): every decision choose the target. *Breachers* are siege units and Siphonarioi; they get an explicit `attack` on the target building (the nearest building when the target is a unit). *Line units* escort them: while the breachers are more than 8 tiles from the target the line attack-moves to a point 2 tiles ahead of the breachers' centroid; otherwise to the target's approach point. A wave without breachers only targets *soft* buildings (resolved melee armour at most 4: Houses, Mills, camps, farms), and above easy only those out of every Town Center's arrow reach (+1 tile) unless the wave's power exceeds 1.2x (all Town Centers' nominal power + the whole enemy army); its line units within 10 tiles of a soft building or of a unit target get an explicit `attack` on it (not attack-move, which would make them retaliate against the Town Center); the rest attack-move (re-sent when the target or point changes by more than 3 tiles, or to idle units more than 5 tiles away). Targets: easy nearest eligible building; standard the 6.5 type priority (production 3, economy 2, House 1, Town Center 0 or 4 with rams) then distance among eligible buildings; hard the same, but only among candidates whose defence (enemy fighting power within 15 tiles plus, for a building in reach of a Town Center, its arrows valued at 300 nominal hp) is at most 1.2x the wave. With no eligible building (standard, hard): the largest villager cluster out of arrow reach and 8+ tiles from every Town Center, then the nearest soft building, then the nearest building. Hard also focuses `attack` on the lowest-hp enemy siege or archer within 6 tiles of the wave every decision. Endgame (no completed enemy producer): nearest villager, then any unit, then any building. The counter matrix in `difficulty.ts` follows the measured duels (spears beat Cataphracts, archers beat swordsmen). Retreat below 30% (standard) / 40% (hard) of start power: `move` to the rally point; the wave ends when all are within 8 tiles or after 45 s. All-in (standard 45:00, hard 40:00): every unit joins the wave, no retreat.
- **Hard commits only when it can win** (`commitRatio` 1.3, `localRetreat` 1.2, `raidFirstWave`). A hard wave launches at its earliest tick only while the massed army's power (6.1 estimate) is at least 1.3x the enemy's whole fighting power; a forced launch needs at least 1.0x, else the forced tick moves 20 s on and it keeps massing; only a nearly full population (190) launches regardless. While attacking, a hard wave pulls back to the rally point when the enemy fighting power within 12 tiles of its centroid plus any Town Center arrows covering it exceeds 1.2x its own power, instead of feeding units. The first wave is a *raid*: it launches in the 7:00-8:30 window with what it has (at least 2 units at the forced tick; in practice 3-5 Spearmen and Horsemen); every unit gets an explicit `attack` on the exposed enemy villager nearest to it (out of every Town Center's reach and 8+ tiles from it); it goes home below half its start power, after 150 s, or as soon as the enemy power around it exceeds 0.7x its own. Measured: against Standard the raid finds the villagers evacuated and the home army waiting and turns back without losses; it costs Standard some gathering time and costs Hard nothing, so its value is low (an attempt to buy four Horsemen for it ahead of the villagers lost a Hard vs Standard seed and killed nothing; reverted).
- **Defence** (6.6). Threat = enemy non-villager units within 20 tiles (footprint distance) of any own building, found through the bucket grid. Clusters by single link (6 tiles); the strongest cluster is answered once the threat has been seen for the reaction delay (10 / 3 / 1 s). Defenders: every own fighting unit except those of a wave more than 30 tiles from home (a wave still near home is ended and joins); they get `attackMove` to the cluster centroid (re-sent when it moves 4 tiles). Standard and hard recall a distant wave when total threat power exceeds twice the defenders'. Enemy siege comes first: when the threat includes a siege unit, every defender gets an explicit `attack` on the one nearest home, and if no enemy fighting unit is within 6 tiles of it, the 6 nearest villagers attack it too (standard, hard). Villagers: easy none; standard evacuates villagers within 10 tiles of any threat unit to beside the Town Center; hard sends the 4 nearest villagers to `attack` a raid of at most 2 units, evacuates otherwise. Held villagers are claimed (the economy leaves them) until no threat has been seen for 10 s; then defenders walk back to the rally point and the economy reassigns the villagers.
- **Repair and rebuild.** Standard and hard: the most damaged completed building below 70% hp with no enemy unit within 8 tiles gets villagers up to 2 (Town Center 4), one building per decision. `desiredBuildings` keeps the most completed buildings per type ever owned; with no Town Center at all (not even a foundation), at least one villager and 100 stone, a Town Center is placed near home with up to 6 builders before anything else; other missing buildings are re-placed (easy: Houses only; standard: everything except Houses, farms, camps and Mills; hard: everything except farms, camps and Mills; the economy places those on demand). Foundations other than farms that nobody builds or walks to get 2 builders (Town Center 4), except while defending (an abandoned camp would otherwise be re-placed by the economy).
- **Unsticking** removed in Phase 3: the sim now walks attackers to the footprint's nearest point, so units no longer wait diagonally beside a building.
- **Decision cost** (6.7) is counted in operations (entities read, candidates scored, grid cells visited, site candidates); `AiPlayer.cost` keeps decisions, total and max. Tests assert an average below 40,000 and a maximum below 120,000 operations per decision; the wall-clock smoke check plays the match twice and keeps the faster run of every decision (machine load slows one run's decision, a really slow decision is slow in both).
- **Not here.** "A unit does not move while `windup > 0`" holds for WP21's own orders; for other orders given mid-swing (e.g. `move`) the movement step skips units with `combat.windup > 0` (wired in Phase 2 integration, below).

## Phase 2 integration (M2)

Rules decided while merging WP21 to WP24 (PLAN-M2 9.5). Where two packages read the plan differently, the plan text decided.

- **Town Center scans run in step 4** (PLAN-M2 2.2: "target scans for due units and buildings"). `scanBuildingTarget` (`defence.ts`) is called from `runAcquisition` in the same ascending-id pass as the unit scans, with the same rules: due when `tick >= attack.nextScanTick`, only without a valid held target (a living enemy unit within reach of the footprint centre), only for a completed living building, and only with at least `ACQUIRE_MAX_CHECKS_PER_SCAN` checks left in the shared `runtime.acquireBudget` (else it stays due; WP21's "exhausted" rule, so no scan is ever cut short). Step 4 reads the positions the index was rebuilt from, so its radius is the exact reach (no pad). Step 8b only decrements the cooldown, re-checks the held target against current positions and fires; a target that died or left reach is dropped with `nextScanTick <= tick + 1` (the 4.6 "target gone" rule), so the next tick's step 4 scans.
- **No movement while winding up** (4.3), whatever the order: `runMovement` neither advances the path of a unit with `combat.windup > 0` (the path is kept; the unit walks on after the release) nor includes it in the separation pass.
- **hp-0 entities are never targets** (4.2), everywhere: acquisition, engagement, Town Center scans and volleys, projectile primaries and splash already skipped them; a unit's wind-up whose target reached 0 hp earlier in the same step 8 now releases nothing (no blow, no projectile). Damage is still applied to every target alive at the moment of the hit, and every unit still completes its release whatever its own hp, so two identical units die on the same tick in either id order (simultaneous damage, 1.2).
- **Kill credit for a dead shooter.** 4.4 credits a projectile to its owner "even if the shooter has died"; 4.9's fallback (a still-flying projectile from the attacker) cannot see the projectile that just landed. `runProjectiles` notes the owner of each impacting projectile's source in a per-runtime scratch (`noteProjectileImpact`, `death.ts`), and `runDeath` uses it after the in-flight fallback, then clears it. A fatal hit in step 9 always dies in step 11 of the same `step`, so the scratch never outlives a tick and is never saved or hashed.
- **Separation keys** (WP24 `isStationaryAttacker`) match WP21's handlers: `attack` in `attacking`, `attackMove` in `engaging`, `hold` with a target, each with no path and no pending request. An attack-move has no separate "attacking" phase, so an engaging unit that stands (in reach, or waiting out the re-path throttle) is pushed like an attacker; one with a chase path is not.
- **Chases use the real `directPath`** within `CHASE_DIRECT_DISTANCE`: it sets the one-waypoint path and drops the unit's queued request itself (WP21's call site also clears `pendingPathRequestId`, which is harmless).
- **The real spatial index** sees only what its step-4 rebuild saw. Entities created later in a tick (none in the real tick order: production runs before step 4) are invisible to queries until the next rebuild; removed ones stay in the unit lists until then and are filtered by `hp > 0` checks. Queries accept `Number.MAX_SAFE_INTEGER` as an unlimited budget (splash).
- **Id permutation.** Units start with `nextScanTick = tick + id % 10` (3.6), so creation order shifts scan phases; swapping the creation order of two ten-unit sides changes nothing but ids (`tests/sim/m2integration.test.ts` (e)).
- **Tests.** WP21/WP22 tests written against the stubs were updated, not loosened: a unit removed at hp 0 reads as dead (the death step removes it in the same tick), system-level projectile and Town Center tests run the real step 4 (index rebuild and scans) before steps 8b and 9. `tests/sim/m2integration.test.ts` holds the cross-package acceptances (ranged kills, projectile credit to a dead shooter, a 20-a-side battle to elimination deterministic through save/load every 100 ticks, conquest defeat ending the match, repair under fire, Town Center kills an attacker, id-permutation independence, the wind-up and shared-budget rules).
## WP29: input and HUD (M2)

Client rules as implemented (PLAN-M2 7.1 and 7.3). Everything here is client-only; no contract file or interface changed.

- **Right click with units selected** (`input/contextual.ts`). An enemy unit or building (owner is another real player, hp > 0) gives `attack` to the selected units that can target it (`combat.attack > 0`; `targets: 'buildings'` units only for buildings); the rest `move` to the target's position (unit position, footprint centre). Repair wins over the farm and drop-off rules (a villager carrying a load to a damaged Mill repairs it; the full-hp Mill takes the load). ## WP30: screens and match (M2)

- **Setup screen** (`app/screens/Setup.tsx`, screen name `setup`, replaces civ select; `civ-panel` is kept). Opponent: Easy, Standard, Hard or "No opponent (sandbox)"; the production and dev default is Standard, the e2e build's default is None (`?opponent=` overrides in dev and e2e, so the M1 suite runs unchanged as sandbox matches). Colours come from `PLAYER_COLORS`: you blue, the opponent red; the colour the other player holds is a disabled swatch (to give yourself red you first move the opponent off it; `?color=red` makes the default opponent blue). The opponent colour row is hidden for "No opponent". Map seed: a text field that takes 0..4294967295 (anything else disables Start), initial value from `?seed` or random, plus a Random button. Config built in `app/setup.ts`: one player `{civ, color, controller:'human'}` for sandbox, or that plus `{civ, color, controller:'ai', difficulty}`; the mode then follows the sim default (2 players: conquest, 1: sandbox). The opponent plays the human's civ (there is only one).
- **Seed pinning.** `host.seedPinned` is true when the seed came from `?seed` or was typed, false after Random or for a loaded save. "Play again" keeps a pinned seed and rolls a new one otherwise.
- **Controllers.** `Match` takes `controllers: Controller[]` (built by the loading screen with `app/controllers.ts`: one `AiPlayer` per player whose `controller` is `'ai'`, restored from the save's block when it has one, else `create(id, difficulty ?? 'standard', state.seed)`). `Match.tick()` drains the human buffer, appends `controller.update(sim)` of each controller in ascending player id, and passes everything to one `sim.step`, so AI commands apply in the same tick as human ones issued in that tick and the sim cannot tell them apart. Controllers do not run while `aiEnabled` is false (`?ai=off`, `__game.ai.setEnabled(false)`) or while their player is `defeated`. Because they are only called from `tick()`, pause, speed and `__game.step` drive them exactly like the human. `host.aiEnabled` carries the flag into new matches.
- **Save and load with controllers.** `ui/saveLoad.ts` keeps the `SaveLoadPanel` signatures: a running `Match` registers a controller-save provider for its sim (`registerControllerSaves`), `saveToSlot` and `exportSim` write `serialize(sim, providers' saves)`; `parseSave` uses `deserializeSave` and parks the file's controller block for the loaded sim (`takeLoadedControllers`), which the loading screen takes to rebuild controllers. v1 files have no block and load as sandbox matches (all players human, so no controllers). `configFromSim` (Restart on a loaded game) copies `color`, `controller`, `difficulty`, `name` and the match mode.
- **End screen** (`app/screens/EndScreen.tsx`, view-model in `app/endScreen.ts`, built by the client from `state.players[].stats`; `HudViewModel.endScreen` is left to WP29 and stays null). `EndWatcher` looks at each tick's events: `MatchEnded` decides (winner = you: victory, no winner: draw, another winner: defeat); a `PlayerDefeated` of the local player without a `MatchEnded` is a defeat on its own (sandbox resign). Reason: `resigned` / `opponentResigned` from the `PlayerDefeated.reason`, else `conquest`. It fires once per match. Showing it pauses the loop; "View map" closes it and unpauses (the match carries on, no second screen), "Play again" restarts the same setup, "Main menu" leaves. The table has one column per player: units trained/lost/killed, buildings built/lost/destroyed, the four resources gathered, techs, peak population and the time each age was reached.
- **Debug hook.** `ai.setEnabled/enabled/memory(id)` (memory = the controller's `save().memory`, null without one); `endScreen()` the current view-model or null; `alerts()` the local player's `UnderAttack` events from the last 3 s of game time (a ping's life: 1.5 s twice), at most 4, `{x, y, tick}` with the tick after the hit; `cursor()` is `attackMove` / `repair` while that input mode is active, else the `data-cursor` attribute the input layer sets on the canvas when it shows the sword (`attack`), else `default`; `startBattle(seed = 1, perSide = 200)` loads `debug/battle.ts` (two lines of the 8.4 mix 14 tiles apart at the map centre, both told to attack-move to the other, built with cheat spawns and `attackMove` commands; no AI controllers) through the loading screen. WP33's `createBattleScenario` may replace it.
- **URL parameters** (dev and e2e only, `app/seed.ts`): `?opponent=none|easy|standard|hard`, `?ai=off`, `?color=<id>`, with `?seed` and `?paused` as before. The screen name `civSelect` is now `setup`.
- **Town Center volleys (4.10).** `runBuildingAttacks` visits completed buildings with `attack !== null` whatever their hp. Reach is measured from the footprint centre to the unit centre (`reach = range + 0.75`). `cooldown` decrements first; a held `targetId` is kept while it is a living enemy unit in reach. With no valid target, `tick >= nextScanTick` and budget left, one scan runs (units only, radius `reach + SPATIAL_QUERY_PAD`, at most `ACQUIRE_MAX_CHECKS_PER_SCAN` checks charged to `runtime.acquireBudget`), choosing the lowest (tier, d squared, id) with tier 1 = `autoAcquire` and `targets: 'any'`, tier 2 = other units; then `nextScanTick = tick + 10`. A scan that finds nothing therefore waits up to 10 ticks. If WP21's acquisition also scans buildings in step 4 and sets `attack.targetId`/`nextScanTick`, step 8b revalidates that target against current positions and does not rescan the same tick; either source works. The volley is `arrows` projectiles from the footprint centre with damage computed at fire time (`attack` vs the target's armour, no bonus) and `flightTicks` from the centre-to-unit distance; then `cooldown = cooldownTicks` (40), so the period is exactly 40 ticks.

## WP28 (overlays, target modes, minimap)

- **Health bars** (`render/overlays`, `WorldOverlays.update`). Drawn for every drawn unit and building (never nodes) of any owner that is selected or has `hp < max`, and not at `hp <= 0`. Own entities are green at 50% and above, yellow from 25% up to 50%, red below 25%; every enemy entity is red (player slot colours are used by the minimap, not the bars). `overlayStats().healthBars` counts them.
- **Art top.** Buildings use `DrawnEntity.top`. The renderer does not set `top` for units, so `overlays/unitTop.ts` finds it: `bounds.minY` plus the fewest empty rows over the frames of the unit's current state and facing (`SpriteAnimation.modelTop`, else a one-time scan of the texture), cached per asset, state and facing (fallback chain `UNIT_STATE_FALLBACK`). It reads the non-team `manifest.sprite`, so recolouring does not matter. If the manifest is missing or the art cannot say, it falls back to `hit.minY`. `DrawnEntity.top` wins whenever the renderer sets it for a unit.
- **Stacking.** A construction or production bar moves above the health bar when both show (`buildingBarCentres`: health at art top + 3 + 2.5 px, progress 8 px higher); alone it stays where M1 put it (6.5 px above the art top). A carried-resource dot moves to the right end of a visible unit health bar.
- **Order markers** (pulse ring, 0.75 s): `attack` (red) at the target's position, `attackMove` (orange) at the point, `repair` (blue) at the building centre, next to the M1 kinds. The same 8-slot ring.
- **Attack-move mode** (`input/placement/attackMoveMode.ts`, `ModeController.startAttackMove()`). The units are the selected own units with `combat.attack > 0` (villagers included). A left click on an enemy unit or building (owner not 0, not local, not a node) issues `attack` for the units whose def can target it (`targets: 'any'`, or buildings only for rams) and `attackMove` to the target's centre for the rest; anywhere else it issues `attackMove` to the point, clamped into the map. Shift sets `queue: true` and keeps the mode; otherwise the mode ends. Right click and Esc cancel without a command. With no unit that can attack, the click toasts "Select units that can attack" and ends the mode.
- **Repair mode** (`repairMode.ts`, `startRepair()`). A left click on an own completed building with `hp < max` issues `repair` for the selected own units whose def `builds` the building's type. Any other click (ground, units, undamaged, unfinished or enemy buildings) toasts "Choose a damaged building of yours" and the mode stays. If no selected unit can build it, it toasts "Select villagers to repair" and ends. Shift queues and keeps the mode. Right click and Esc cancel.
- **`ModeController`** gains `startAttackMove`, `startRepair`, `target` (the active target mode), `modeKind()`, `cursor()` and `destroy()`. `active` keeps its M1 meaning and type (placement or rally only; null in a target mode) because the debug hook's `inputMode()` is typed by it; `onChange` and `ActiveMode` cover all four kinds. The helpers in `targeting.ts` (`canTarget`, `anySelectedCanTarget`, `resolveAttackMoveCommands`, `repairers`) are exported for the contextual right click (WP29).
- **Cursors** (`cursors.ts`, owned by the mode controller, which listens to `mousemove` and `mouseleave` on the world canvas and to selection changes): data-URI SVGs drawn in code. `attackMove` (crosshair) in attack-move mode, `repair` (hammer) in repair mode, `attack` (sword) while no mode is active and the pointer is over an enemy that a selected own unit can target, else the page cursor. `modes.cursor()` returns the kind (what the hook's `cursor()` should report).
- **Dev and e2e handle.** In dev and e2e builds the controller defines `window.__game.wp28 = { startMode(kind), cursor(), modeKind() }` (non-enumerable, removed on `destroy`) so specs can enter the target modes before the command card (WP29) and the hook (WP30) do it.
- **Minimap.** Units are 3 px in the owner's slot colour for every player (the enemy used 2 px); buildings were already in the owner colour. Pings: `minimap.ping(x, y, color?)` (default red `0xff4a3a`) adds an expanding ring on its own canvas between the base and the camera outline. Timing is the match clock only: age is `state.tick - ping.tick`; one ring takes 30 ticks (1.5 s) and plays twice (60 ticks), at most 4 live (a fifth replaces the oldest), a repeat of the same place on the same tick is ignored, and pings from a later tick than the state (after loading an earlier save) are dropped. The canvas is redrawn only when the tick or the ping count changes, so pausing freezes the rings. `minimap.alerts()` returns the live pings `{ x, y, tick }` (the hook's `alerts()`). `MinimapDeps.events` (optional, `Match.onEvents`) makes own `UnderAttack` events ping without more wiring; it is not connected in `app/hooks.ts` (not WP28's file).

## Phase 2 client integration (M2)

Decisions taken while running WP28, WP29 and WP30 together against real combat (PLAN-M2 9.5).

- **Target modes.** The command card's Attack-move and Repair buttons (and A / R, which go through the same card slots) call `HudControllerOptions.onStartAttackMove` / `onStartRepair`, wired by `GameScreen` to `match.modes.startAttackMove()` / `startRepair()`. The temporary `window.__game.wp28` handle is gone; `GameDebugHook.inputMode()` (additive contract change) reports `'placement' | 'rally' | 'attackMove' | 'repair' | null` from `modes.modeKind()`. `Match.destroy` destroys the mode controller (silently: no mode-change callbacks during teardown).
- **One targeting rule set.** The contextual right click, attack-move mode and the sword cursor all use `input/placement/targeting.ts`: `isEnemyOf` (a living unit or building of another real player; hp-0 entities are never targets, as in the sim), `canTarget` (rams: buildings only) and `repairers`. `resolveMaxHp(query, registry, owner, typeId)` there is the one max-hp lookup (resolved stat, else the def's base hp) for the health bars (cached per owner in `MaxHpCache`), the selection panel, the right click and repair mode.
- **Cursor.** `ModeController.cursor()` is the one source; the cursor controller also mirrors the kind on `canvas.dataset.cursor` (absent for the default) and the hook's `cursor()` reads `modes.cursor()`. The cursor is recomputed on pointer moves, selection and mode changes, so a sword over an enemy that dies under a resting pointer stays until the pointer moves.
- **Alerts.** Every own `UnderAttack` is handled once, by the HUD's `NotificationCenter`: the toast (throttled per kind, 15 s of client clock), `input.noteAlert` (the `Space` target) and `onAlert`, which `GameScreen` points at `match.minimap?.ping(x, y)`. The minimap no longer subscribes to events itself and `Match` keeps no alert log; `__game.alerts()` returns the minimap's live pings (empty before the minimap is mounted). An own `BuildingDestroyed` while the local player is already defeated (resign, conquest: everything goes at once) raises no toast.
- **End screen.** `Match.endScreen` (from `EndWatcher`) is the one mechanism; `HudViewModel.endScreen` stays null. While it is shown, `GameInput.suspended` drops canvas clicks and every hotkey, so Space, Pause or Esc cannot resume, order or open the menu behind it; "View map" clears it.
- **Draw only changed frames** (`render/redraw.ts`). Pixi redrew the whole stage on every animation frame. With software GL (the e2e browser and machines without a GPU) a redraw plus the compositor's readback of the canvas held the page's main thread for about 150-200 ms per frame, paused or not, and every Playwright action that waits for frames paid it several times. The application's render ticker entry is replaced by one that draws only when a scene signature changes (per visible node: position, scale, rotation, alpha, tint; sprites: texture uid, frame origin and anchor; other nodes: Pixi's view-change counter; plus the screen size), with a forced draw every 60 frames. Pooled overlay sprites that are reset and set back to the same values compare equal. Unit sprite animations now run on game time (`(tick + alpha) * 50 ms`) instead of wall time, so a paused match is a still picture (and idle animations follow the game speed). Measured on the same machine at load 7-8: an idle paused frame 211 ms -> 19 ms; phase2 scenario 8 66 s -> 20 s, scenario 9 57 s -> 28 s. The Milestone 1 build measured the same 60 s / 56 s under that load, so scenarios 8 and 9 had not become slower in M2: they were always bound by per-frame GPU cost, which grows with machine load.
- **E2E.** `tests/e2e/combat.spec.ts` plays plan 8.2 scenarios 2 to 12, 14 (a conquest: rams right-clicked onto the enemy Town Center, cavalry attack-moving through the villagers, until `winner === 1` and the victory screen) and 16, plus save and load mid-fight, in `?opponent=standard&ai=off` matches with spawned units, real clicks verified by `pickAt` (ground clicks verified to pick nothing) and stepped time. Fights are staged at least 13 tiles from the own Town Center so its arrows do not decide them. Checks that need WP27 (`effects()` corpses, projectiles, fires, rubble) are `waiting` annotations; scenario 8 asserts the Town Center kills the horseman unaided and records the time (about 450 ticks with the current data, plan target 300: a balance question). Scenario 4 switches stance soon after the first arrow because archers counter spearmen. wp28's mode specs enter the modes through the card; wp30's scenarios 13 and 14 run unconditionally.

## M2 balance

WP32 tuned the combat numbers against the real sim (`docs/BALANCE.md` has the duel table, the siege rows and the feel numbers). Only `src/data` changed; no sim code and no economy number. Append-only list of what moved and the rules that follow from it:

- **Building melee armour** (approved by the orchestrator): Barracks, Archery Range, Stable, Siege Workshop and Silk Workshop 2 to 7; Town Center 3 to 8. A Swordsman, Spearman, Villager or Archer does 1 damage a blow to them (the damage floor), so **only siege, Cataphracts and Siphonarioi can raze production buildings**; 2 Rams take a Barracks in 48 s, 10 Swordsmen 440 s. Houses (1), Mills and camps (1) and Farms (0) are unchanged: 5 Swordsmen take a House in 36 s. Pins: `computeDamage(ram, barracks)` is `1 + 60`, the Town Center's `meleeArmor` is 8.
- **Archer bonus against infantry** +4 to +5 (Archer against Swordsman and Spearman now 9 a hit). Reason: Archer against Swordsman flipped to a loss at a budget of 600 and fell to 22% survivors elsewhere; at +5 it keeps at least 50% of the Archers at every budget from 300 to 3000. Pin: `archer` against `swordsman` 9.
- **Battering Ram cooldown** 4.0 s to 3.5 s: 2 Rams destroy a Barracks in 48 s (was 52.5, limit 60).
- **Siphonarios splash radius** 1.0 to 1.25 (percent stays 60): 4 Siphonarioi are 5.0x 4 Swordsmen against the harness clump (was 2.52x against the 2.5x needed). Pin: `splash` `{ radius: 1.25, percent: 60 }`.
- **Unchanged on purpose:** Town Center arrows (5 pierce, 2 arrows, range 7: raising the attack to 6 changed no matrix or raid result), every cost, train time and economy number, Archer cooldown 1.6 s and Cataphract attack 13 (WP25).
- **Rules the AI and the UI can rely on:** attack-moving into Town Center range makes units retaliate against the Town Center (tier 0 target) and waste their blows; raids on workers and siege escorts need explicit `attack` orders. Villagers, Spearmen and Archers move at 1.0, so infantry cannot catch a fleeing Villager. 3 repairing Villagers hold a House or Barracks against 3 infantry or cavalry attackers and lose to siege and splash.
- **Tests:** the duels (`tests/sim/duels.test.ts`) run every 5.3 cell and siege row on the real sim, also at three army sizes and with the creation order swapped; `tests/sim/feel.test.ts` holds kill times, raids, repair and upgrade effects (harness in `tests/sim/feelHarness.ts`). `COMBAT_INTEGRATED` is permanently true. The duel harness's winner is decided by who still has fighters (a wiped side used to read as "none"). The integration test "an army destroys an undefended base" now brings two Rams, and the skirmish determinism test checks that both sides were hurt at tick 600 rather than 900 (one side is wiped by then).

## WP33: combat hardening, performance and determinism

Rule changes (sim):

- **Reaching a footprint** (`combat/engage.ts`, `stepIntoReach`). A footprint path ends on a ring tile 8-adjacent to the footprint, but from most of such a tile (a corner tile away from the corner, the far half of a side tile) the footprint is beyond the base reach of 0.75; the next request returned an empty path ("already at the goal") and the unit stood forever (seen: a Spearman diagonally 0.84 from a Barracks; the AI unstuck 22 units). Now a unit chasing a building with no path left to follow (none, used up or empty) and within `reach + 1.5` of the footprint walks straight towards the footprint's nearest point and stops `reach / 2` from it (`(minRange + reach) / 2` for a unit with a minimum range), when that segment is walkable (it stays inside the unit's own tile from a ring tile). This also returns a stationary attacker that separation pushed out of reach. Checked for every attacking unit type against footprints of size 1 to 4 from all 8 directions and a Barracks ringed by 24 melee attackers (`tests/sim/combatReach.test.ts`).
- **Unreachable targets.** A chase whose last served A* path is empty (the unit already stands on the reachable tile nearest the goal) and still out of reach, with no direct step possible, is `unreachable`: a commanded or auto `attack` ends (`done`, next scan after a full `ACQUIRE_INTERVAL_TICKS`), an attack-move engagement resumes walking with the same scan delay. Before, such a unit re-requested the same empty path every 10 ticks forever.
- **Hardened targets** (PLAN-M2 4.5 "Hardened targets"; `isHardened`, `autoTier` in `engage.ts`, used by `acquire.ts`). A building is hardened against a unit when the unit's damage per blow against it is at most `minDamage` (armour of the unit's attack type at least its attack, no bonus): with the M2 data infantry, cavalry and archers against production buildings and the Town Center, never siege, Cataphracts or Siphonarioi. In automatic target choice (acquisition, retaliation, retargeting, hold; never commanded `attack` orders) it is tier 4, below every unit and every other building; it is never the tier-0 last attacker; it is no candidate for an attack-move that is still walking; and a unit whose auto, attack-move or hold engagement holds one rescans every interval (sight; reach for stand ground and hold) whether or not it is in reach, switching to anything of tier 3 or lower. So 5 Spearmen attack-moved at the Villagers beside a Town Center kill them (before: wiped, Villagers untouched), an army attack-moving past a Town Center walks on, and units that arrive with nothing else in sight still take on the Town Center (which the AI's endgame relies on). This supersedes the "M2 balance" note that attack-moving into Town Center range makes units retaliate against it.
- **Town Center arrows** 5 to 7 pierce (data; `docs/BALANCE.md` change 8): a lone idle Horseman 3 tiles from a Town Center dies in 248 ticks (was 448; plan 8.2 scenario 8 about 300, e2e now asserts within 400), a 5-Horseman raid on the workers loses 1 unit (was 0), infantry and archer raids of 5 keep 2 to 4 (Archers 2). `tests/sim/feel.test.ts` asserts both.

Verification:

- **Combat fuzz** (`tests/sim/combatFuzz.ts`; bounded in `combatFuzz.test.ts`, 50 seeds x 4,000 ticks in `combatFuzz.long.test.ts`). A 40x40 two-base map with tree pockets, every soldier type and villagers; seeded random commands (attack incl. siege on units and unknown targets, attack-move mostly towards the enemy, hold, setStance, repair, move, stop, delete of units and buildings, resign late) in bursts of 300 ticks followed by quiet stretches of 500 in which orders play out. Invariants after every tick: no current order names a removed entity on two consecutive ticks; a unit with a live `attack` or `attackMove` moves, winds up, attacks or changes order (type, phase, target) within 300 ticks; no hp-0 entity is present a tick after it was first seen at hp 0; `canonicalJson` never throws; no accumulator negative or non-finite, resources, carried amounts and hp non-negative integers, hp within the resolved maximum; `popUsed` equals the living units; every removed unit or building died (event) or was deleted; the death stats move exactly with the death events and never credit the owner. Hashes agree over two runs and across a save/load at a seeded tick. Findings: with the footprint fix disabled it reports the stuck chasers within the first seeds (the defect above); with the fixes, 50 seeds x 4,000 ticks (29 of them ending in a resignation) are clean. Nothing else was found.
- **Battle scenario** (`createBattleScenario(seed, perSide = 200)` in `src/sim/stress.ts`, plan 8.4): the generated two-player map with both bases and starting villagers, 30 completed buildings per side around its Town Center (3 Barracks, 2 Archery Ranges, 2 Stables, a Siege Workshop, a Mill, 2 Lumber Camps, a Mining Camp, 6 Farms, 12 Houses), and per side 60 Spearmen, 40 Swordsmen, 34 Horsemen, 10 Cataphracts, 40 Archers, 10 Siphonarioi, 4 Rams and 2 Trebuchets (the plan's mix with 6 Horsemen traded for siege; scaled for other sizes, remainder to Spearmen) in rows at the map centre 14 tiles apart, written into state (no cheats). The function steps once with one `attackMove` per side towards the other line, so the sim it returns is at tick 1. The client's `src/client/debug/battle.ts` stand-in (cheat spawns) can switch to it; that is the client owner's change.
- **Performance tests.** `tests/sim/perfHarness.ts` runs the same deterministic scenario three times: the average is the best run's thread CPU time per tick (`process.threadCpuUsage`, read around the whole window because it ticks in 4 ms steps), p99 and max come from the per-tick best wall time over the runs. A noisy neighbour slows one run's ticks, not the same tick in all three, so this no longer fails under load while a real hot tick still counts. `npm test`: the stress budget (average < 2 ms, p99 < 12 ms, max < 60 ms) and a battle smoke (100 a side, ticks 200 to 600, average < 4 ms, p99 < 12 ms); `npm run test:long` (`performance.long.test.ts`): the full battle, ticks 200 to 2,200, average < 4 ms and p99 < 12 ms, plus the clash (ticks 1 to 700) reported under the same budget.
- **Profiling and fixes** (behaviour-preserving: the battle hashes every 100 ticks to 2,200 for seeds 1 and 2, the 30,000-tick two-economy-bot run every 1,000 ticks and a 30,000-tick Hard vs Standard AI match every 1,000 ticks were identical before and after). The profile is flat (no function above 9%): the per-tick loops over every entity dominate, because the 120 map holds about 1,800 resource nodes. `unitsThisTick` (`combat/spatial.ts`) hands steps 5 to 8a (orders, movement and separation, unit attacks) the unit list of the step-4 index rebuild, valid while no entity was added or removed since (checked by tick, entity count and `nextEntityId`; otherwise callers iterate `state.entities` as before); acquisition tests a candidate from the index with `canTarget` instead of looking its id up again; repair no longer allocates a fresh empty `repairerIds` for every completed building every tick. Single runs under that load show 5 to 100 ms wall spikes that the best-of-3 removes. Both budgets hold with a wide margin; chases request about 6 paths a tick at the height of the clash (400 units).

The battle runs twice and with a save/load every 250 ticks, identical every 100 ticks (`performance.long.test.ts`). Id order: the existing permutation tests (WP21 duels, budget deferral, the mirrored fight of the Phase 2 integration) still hold; `combatReach.test.ts` adds a crowded building whose 18 attackers created in reverse order play out identically.
- **For the AI owner:** the WP26 "Unsticking" workaround (`move` to 0.3 tiles outside a footprint for chasing units with no path) is no longer needed and can be removed; so can the explicit-`attack` raid workaround for attack-moves near a Town Center, if the AI wants (attack-move now takes the units first), though explicit attacks still work.

## WP27: renderer and effects (M2)

PLAN-M2 7.2 as implemented (`src/client/render/effects/`, `render/entities.ts`, `src/client/art/`). Client-only: nothing here is in state, saved or hashed.

- **One state fallback.** `UNIT_STATE_FALLBACK` (`art/manifest.ts`) is a chain over every `UnitAnimState`, ending at `idle`; `resolveUnitState(states, wanted)` walks it and is used by the renderer, the overlays and the sheet manifest alike. The sheet branch's `GENERIC_STATE` and the sheet manifest's alias table are gone.
- **Game time everywhere.** Every animation (idle, walk without a `cycle`, work, attack, death, effects, fires, `__art.preview`) is timed by `(state.tick + alpha) * 50 ms`; nothing reads a wall clock, so pausing freezes the picture, the game speed drives it, and `redraw.ts` still skips unchanged frames (a paused battle with corpses, fires, flashes and arrows in the air keeps one scene signature: `tests/unit/client/effects.test.ts`).
- **Attack animation.** A unit shows `attack` while `combat.windup > 0` and for `ATTACK_ANIM_TAIL_TICKS` (8) ticks after `lastAttackTick`, over any other state. Wind-up ticks come from the data (`max(1, round(windup * 20))`; no upgrade changes them). Frames `0..hitFrame` are spread over the wind-up with `elapsed = windupTicks - windup + alpha`; the state after the release step (`tick === lastAttackTick + 1`) shows exactly `hitFrame`; the remaining frames play over the tail. Art without an attack animation (the voxel fallback units) lunges 3 px along its facing instead. Hit frames: the procedural attack is two frames, blow on 1; the sheets take a per-unit table read off the Blender rigs (frame 5 for the spear and lance lunge, sword and mace strike, javelin throw, bow loose and ram swing; 4 for the villager's axe and the trebuchet's throw; 3 for the siphon's full stream), which a sheet's own `hit` overrides (`sheet/manifest.ts` `sheetHitFrame`).
- **Hit flash.** A unit with `lastDamagedTick === tick - 1` (2 ticks, alpha included) is overdrawn by a white silhouette of its current frame at 40% (`whiteOf`: one small canvas per texture that has flashed). Where a texture's pixels cannot be read, there is no flash.
- **Work.** A villager in a `repair` order's `repairing` phase animates like a builder (`work`, `build` on the sheets) and faces the building.
- **Layers.** World children back to front: terrain, ground shadows, `effects.decals` (rubble, then corpse shadows, then corpses, sorted by screen y), ground overlays (selection rings, markers), entities (with the building fires), `effects.fx` (projectiles and one-shot effects), world overlays (bars). Corpses therefore lie under every living unit and every ring.
- **Event time.** `Match.tick` calls `pushEvents` right after `sim.step`; the sim mutates one state object, so the layer stamps events with the tick of the last state it drew, which is already the tick after the step. Events pushed before any frame are kept and stamped with the first state drawn. The layer clears itself when the state it draws is a different object or goes back in time (a load), so a loaded game has no corpses or rubble (PLAN-M2 2.5).
- **Corpses.** `UnitDied` plays the unit's `death` (owner colour, event facing) once, then holds `corpse` (sheets) or the last death frame, for 20 s of game time, fading over the last 3 s; at most 300 (the oldest, by birth tick, go first). Art without a death animation tips its idle figure over backwards in 0.4 s and darkens it.
- **Rubble.** `BuildingDestroyed` (foundations too) leaves `rubble.<size>` (sizes outside 2..4 scale the nearest; the variant is chosen by the building id) for 60 s of game time, fading over the last 3 s, at most 60, and raises five `fx.dust` clouds (the middle, then the four corners 60-270 ms later), scaled by the footprint.
- **Projectiles** are drawn every frame from `state.projectiles`, culled to the view plus 200 px: `lerp(from, to, p)`, `p = 1 - (ticksLeft - alpha) / flightTicks`, lifted by `4 H p (1 - p)` (arrow 0.4, stone 1.5 tiles; `iso.ts` `worldToScreenZ`, 39.2 px per tile of height) and 10 px (chest height). Arrows are rotated to their screen velocity (ground plus arc); stones are not rotated. Fire is a stream from the nozzle (11 px up at `from`) to its head (4 px up), stretched and rotated, its 3 frames flickering. A projectile drawn on the previous frame (at most 3 ticks earlier) and gone now leaves `fx.hit` (arrow, 10 px up, scale 0.8), `fx.dust` (stone, 0.75) or `fx.splash` (fire) at its last `to`.
- **Melee sparks.** On each new tick the layer looks at units whose `lastAttackTick` is at or after the last tick it processed and whose def has no projectile: `fx.hit` 70% of the way to a unit target (12 px up), on the footprint point nearest the attacker for a building (14 px up), else 0.55 tiles ahead along the facing. Hits, impacts and sparks are seen by the renderer only: ticks stepped without a frame (`__game.step(n, false)`, `stepUntil`) show none; `effectStats().effects` counts the live ones.
- **Building damage.** Completed, living buildings with `hp / builtHp` (once constructed `builtHp` is the resolved maximum, so the renderer needs no query) below 0.66 show one `fx.fireSmall` and `fx.smoke`; below 0.33 `fx.fireLarge` at 2 points (3 for footprint 4) and one smoke. The points are evenly spaced around the footprint centre from a start angle hashed from the building id, 0.12 to 0.32 of the side out, raised 30-65% of the building's art height (from `DrawnEntity.top`) and pulled 25% towards the anchor so they stay on the art. They are drawn in the entity container just in front of their building (`z + 0.3` smoke, `z + 0.4` fire) and so behind any unit standing in front of it; each building's flames run with their own phase.
- **`effectStats()`**: `projectiles` = projectiles in state (held, drawn or not), `corpses`, `rubble`, `fires` = fires over all completed buildings (smoke not counted), `effects` = live one-shot effects (at most 400).
- **Effect art.** `art/fx.ts` draws the projectiles, hits, dust, splash, fires and smoke (soft radial-gradient puffs that loop seamlessly) for both art modes, and procedural rubble. The rendered art claims `rubble.*` and voxel-renders it in the background pass (`models/rubble.ts`: a heap of broken walling over the footprint, wall stubs at some corners, charred beams at all angles, soot, spilt blocks; two variants per footprint), serving the procedural rubble until it arrives. Effect sprite ids (`catalog.ts` `EFFECT_SPRITE_IDS`) are not entity sprites; `classifySprite` knows them.
- **Unit attack and death art.** Sheets: their own `attack` (8 frames), `death` (7, once) and `corpse`. Procedural (`?art=fast`): `attack` is each painter's work pose (every soldier's is its blow) with the figure leaning back 0.8 px on frame 0 and lunging 2.2 px on frame 1; `death` is three frames made from the bare idle figure (no ring or shadow): kneeling (squashed), falling (tipped about the feet) and lying (tipped further, flattened to 62% into the ground plane, darkened, with a shadow); horses and siege engines tip less and collapse. Voxel units have no attack or death frames (the sheets cover every unit); the renderer's lunge and tip-over cover them.
- **Icons.** The 12 military upgrades have their own icons: the line's glyph (swords, bow, horse), a badge (raised blade for attack, shield for armour) and the level (I, II). Sheet portraits of foot units show the head and upper body (the top 60% of the figure) and every sheet portrait may scale up to 4x with nearest sampling, so they fill the frame.
- **Late art and the HUD.** The rendered art's background pass calls `notifyArtUpdate()` (`art/updates.ts`; also `TeamAssetManifest.onUpdate` per manifest, forwarded by the composite). The HUD gives `IconContext` a new resolver identity on every update, so icons drawn before their sprite existed (later-age buildings' portraits, which were blank squares) are read again.
- **Cursor.** The mode controller recomputes the canvas cursor every frame (`GameInput.onFrame`), not only on pointer moves and selection changes: a sword over an enemy that dies under a resting pointer, or after the camera or the selection changed by a hotkey, goes at once. This supersedes the "Phase 2 client integration" note that it stayed until the pointer moved.
- **Battle scene.** `debug/battle.ts` (`__game.startBattle`) now loads WP33's `createBattleScenario(seed, perSide)` (a sim at tick 1) instead of its cheat-spawn stand-in.

## WP34: UX pass, edge cases and art fixes (M2)

Found by playing a full conquest match against the Standard AI in the browser build (rendered art, seed 3, 1280x720 and 800x600, real pointer and keyboard input; won at 1:06:36) and by the plan's edge cases (PLAN-M2 9.6). Client only: no sim, bot, data or contract file changed.

- **Foundation health bars.** A building under construction holds only the hp construction has granted (`builtHp`, PLAN-M2 4.11), so every foundation showed a mostly empty health bar, red for the enemy, as if it were badly damaged. `healthBarShown(hp, max, selected, intactHp)` now measures damage against `intactHp` (`builtHp` for a foundation, the resolved maximum once built): a foundation shows a bar only when selected or hit. The construction progress bar is unchanged.
- **Target mode hint.** Attack-move, repair and rally modes were shown only by the cursor. While one is active the HUD shows a hint above the bottom panel like placement's ("Attack-move: click the ground or an enemy. Shift keeps the mode, Esc or right click cancels"; `MODE_HINT_TEXT`, testid `mode-hint` with `data-mode`), wired from `Match.onModeChange` in `GameScreen` (`HudProps.targetMode`; additive, `HudViewModel` unchanged). Placement keeps its own hint; the two never show together.
- **Soldiers first in a drag box.** A box over an army walking through the fields also took the villagers, and the shared card of villagers and soldiers is Stop only, so the army could not attack-move. `boxSelection` takes an `isWorker` test (a unit whose def can gather): when the box holds at least one own non-worker, the workers in it are left out; a box over villagers alone still selects them; Shift keeps what was selected and adds only the boxed soldiers. Clicks, Shift-clicks and double-clicks are unchanged, so a mixed selection can still be made on purpose.
- **Large selections.** The multi-selection grid showed two rows of 40 px portraits and cut the third in half; from 29 units on the rest were simply not shown. Above 16 entities the portraits are 28 px (`MULTI_DENSE_FROM`); the grid shows whole rows only (two normal, three dense) and scrolls by rows (scroll snap), so no portrait is ever clipped.
- **One idle-villager toast.** Each batch of `VillagerIdle` events made its own toast and identical texts merged by counting batches, so "A villager is idle x11" and "2 villagers are idle x2" stood side by side and neither said how many were idle. There is now one idle toast; each batch updates its text to the number of own villagers idle now (no order, queue, path or pending path; at least the batch's count) and restarts its lifetime.
- **Repair without resources.** A repair tick that cannot be paid changes nothing (PLAN-M2 4.12) and the sim emits nothing, so the villagers hammered on with no feedback. The HUD looks on each refresh: an own building with repairers, below its maximum hp, that has gained no hp for `2 * ceil(20 / repairMinHpPerSecond)` ticks (a working repair always gains in that time; hp lost to attackers meanwhile does not count as progress) while its cost holds a resource the player has none of, raises one error toast per stall: "Not enough wood to repair" (`repairStalledText`). Repair is bought a fraction at a time, so with none of a resource it still runs until the next whole unit is due; the toast waits for that. The stall ends when hp rises again.
- **The match ends with the menu open.** The end screen used to open over the in-match menu (or its Resign question) and leave the menu's pause bookkeeping behind; the defeat banner, the conquest objective banner and a burst of "destroyed" toasts queued behind it and played after "View map". `HudMatch` gained optional `endScreen` / `onEndScreen` (WP30's `Match` already has both): when the end screen opens the HUD closes the menu and the Resign question, forgets the menu's pause (the end screen holds it), and drops every toast and banner; while it is shown, events are not announced. After "View map" the HUD announces again.
- **Setup screen at small sizes.** At 640x480 and 800x600 "Standard" overflowed its button. The opponent row uses `minmax(0, 1fr)` columns, 2 px side padding and no wrapping.
- **Edge cases checked and covered** (`tests/e2e/wp34.spec.ts`): a mixed selection with a ram (right click on a unit: the others attack, the ram walks to the target's position; attack-move and a right click on a building take every unit); repair while unaffordable; resigning while paused (the menu closes, the toast, nothing moves until the next tick, then the defeat screen); the match ending with the menu and the Resign question open; units dying out of the selection, the selected enemy dying while inspected, control groups recalling survivors and a dead group doing nothing (no camera jump); toasts during mass death (12 villagers killed by a raid: one alert toast, at most four toasts, at most four pings; three Houses falling in one tick: "House destroyed x3"). The shared helpers of the combat specs moved to `tests/e2e/combatHelpers.ts`.
- **Building fire as pixel art** (`art/fire.ts`, used by `art/fx.ts` for both art modes). Supersedes the WP27 flames (flat bezier tongues in three bright fills) and soft gradient smoke. Each pixel is computed at the scene's resolution (one texel per screen pixel at 1x, crisp at every zoom) from turbulence (three octaves of value noise) that scrolls up exactly one period per loop, so the 8 frames (90 ms each) loop seamlessly; colours follow a gritty heat ramp (soot-dark red, rust, ochre, gold, hot white at the cores) and are reduced to the shared 256-colour palette with an ordered 4x4 dither (still pixels stay still from frame to frame). Each fire carries a static soot scorch on the wall around and above it (the sprite's top rows hold soot only) and a few single-pixel sparks. Smoke is a dark column of billows (8 frames, 150 ms) that rises, leans and thins with ordered transparency. Small fire 20x30 px, large 34x52, smoke 36x80; the large sprite is the bigger fire, so the layer no longer scales fires up (smoke grows 10% per footprint above 2). Still game time and redraw-on-change: a paused scene keeps one signature.
- **Projectiles at every zoom.** `projectileScale(zoom)` keeps an arrow (12 px of art) between 12 and 18 screen px: 2x the sprite at 0.5x (it was 6 px there), 1:1 from 1x to 1.5x, 0.75 at 2x (it was 24 px). Stones and the fire stream's thickness scale the same way. `EffectLayer.update` takes the camera zoom.
- **Unit scale, checked, unchanged.** A sheet villager or swordsman stands 24 to 27 px above its ground anchor at 1x (0.61 to 0.69 tiles of height at 39.2 px per tile); the voxel human it replaced was built 0.6 tiles tall (about 23.5 px), the same height the Blender rigs use (`UNIT_H` 0.6). Voxel doors are 0.29 to 0.6 tiles tall (a stone House 0.42, a Barracks 0.5, the Town Centers 0.36 to 0.59, the smallest 0.26). So the figures are as tall as the voxel units they replaced and already as tall as or taller than every door (a real 1.72 m figure would be about 0.8 of a 2.1 m door); they look small because the buildings are large, the usual RTS convention. Draw scale, click boxes, bar anchors and rings are unchanged.
- **Screenshots.** `docs/screenshots/14-battle.png`, `17-battle-arrows-2x.png`, `18-burning-town-rubble.png` and the new `20-battle-0.5x.png` were regenerated with `node scripts/art-shots.mjs <dir> battle` (`19-corpses.png` came out byte-identical). The script starts its own preview server with `--strictPort` and ignores its output, so if `SHOT_PORT` is already taken by another server it silently photographs that server's (older) build; check the port is free first.
- **Not fixed (outside the client, or a design call):** after a Town Center falls, production buildings that infantry and cavalry hit for 1 a blow (M2 balance) keep a conquest going for a long time without siege (data); a selected army of 100 shows a solid slab of health bars over itself (the plan shows bars for every selected unit); at 800x600 the top bar wraps into two rows (WP29 layout, still clear of the view's centre).
- **Tests.** `tests/e2e/wp34.spec.ts` (12 tests: the edge cases above, the foundation bar, the mode hints, a 48-unit selection at 1280x720 and 800x600, the idle toast, the setup screen at 640x480 and 800x600); `tests/unit/client/fireArt.test.ts` (palette-only colours, hot cores and soot, the loop closes, determinism, smoke darker near the fire, projectile sizes per zoom); additions to `selection.test.ts` (soldiers first), `wp28.test.ts` (foundation bar), `notifications.test.ts` (one idle toast) and `hudController.test.ts` (repair stall, end screen over the menu).
